# OKF 導入の実証実験

計画Issue #284 で、`docs/` を [OKF v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) のバンドルにした。第一目的は、**この運用で OKF が有用かを判断すること**であり、docs と実装の乖離の解消は手段の一つ。運用の約束は [okf-conventions.md](./okf-conventions.md)、乖離の監査結果は計画Issue #284 のコメントにある。

この文書は、評価観点を導入時に先に定め、所見と結論を追記していく記録である。観点と判定基準は、結果を見てから変えない(変えるときは理由を所見に書く)。

## 評価観点と判定基準

| # | 観点 | 見るもの | 継続とみなす目安 | 見直しとみなす目安 |
|---|---|---|---|---|
| 1 | 乖離の検出・防止に効いたか | `npm run docs:check`(CI の `docs-check` ジョブ)が、実際の乖離を検出して修正につながった回数 | 再評価までに、実装側の移動・削除などによる乖離を1件以上検出した | 検出が0件で、誤検出による修正だけが発生している |
| 2 | 導入と保守のコスト | PR あたりの docs 関連の追加作業(frontmatter・`index.md`・`log.md`・`docs:check` の失敗対応)、`doc-updater` の手順の増加量 | 通常の PR の追加作業が数行の編集にとどまる | 本文の更新より、形式の保守に時間がかかる PR が続く |
| 3 | AI エージェントが必要な知識を見つけやすくなったか | `planner`・`evaluator`・`doc-updater` が、`index.md` や `description` を手がかりに、必要な文書へ辿り着けたか(作業中の観察で、辿り着けなかった例を記録する) | 導入前(`domain.md` の表だけ)より迷わず辿り着けた例がある | 導入前と差が無い、または `index.md`・`description` が実態とずれて誤誘導した |
| 4 | 仕様変更への追随しやすさ | 仕様の版が上がったときに、チェックと docs の修正にかかった工数 | 規約の手順(「仕様の版が上がったとき」)どおりに半日以内で追随できた | 破壊的変更のたびに大規模な書き換えが要る |

## 再評価のタイミングと記録先

- **再評価**: OKF 導入後に docs を更新する PR が10件マージされた時点、または OKF の版が上がった時点のいずれか早い方。
- **記録先**: この文書の「所見」に、日付つきで追記する。継続・見直し・中止の結論もここに書く。
- 見直しの場合の候補: 運用の縮小(`index.md`・`log.md` の廃止や frontmatter の項目削減)、`decisions.md` などの分割(別 Issue)、OKF からの撤退。

## 所見

### 2026-11-25(導入直後)

**事実として確認できたこと**

- **導入作業**: 19ファイルへの frontmatter の付与は、スクリプトで一括で行えた。人手で決めたのは各文書の `type`・`description`・`resource` だけだった。準拠チェックは純粋関数と34件のテストで実装し、SPEC の適合条件の検査に絞った。SPEC に lint は無く、自作が必要だった(観点2)。
- **乖離の監査**: 参照の実在を機械検査すると、存在しないパスが38件・識別子が70件出たが、要修正は2件だけだった。残りは、履歴ログに残る過去の状態の記述と、検査の誤検出(ブラウザの `WebAssembly.CompileError` など)だった(観点1)。
- **resource による検出の設計**: 現行の文書(`domain/*.md`)にだけ `resource` を付け、履歴ログには付けない運用にした。履歴ログに付けると、過去の状態を指す記述が必ず誤検出になるため。`type`(`Decision Log` など)で履歴ログと現行の文書を区別できることが、この運用の前提になった(観点1)。
- **構造の不一致**: `decisions.md`(約1,900行)・`patterns.md`・`knowledge.md` は追記専用のログで、OKF の「1ファイル1概念」に合わない。粒度は維持し、型で履歴ログと示した。分割は別 Issue で判断する(観点2)。

**まだ検証できていないこと**

- 実際の乖離を `docs:check` が検出するかは未検証。導入直後は違反が0件で、検知の実績が無い(観点1)。
- 本文の内容が実装と一致しているかは検査できない。`resource` の存在確認は、移動・削除の検出にとどまる(観点1)。
- AI エージェントが `index.md`・`description` で見つけやすくなったかは、導入直後で観察できていない(観点3)。
- 仕様の版が上がったときの追随工数は、まだ版が上がっておらず不明(観点4)。

**暫定の結論: 継続**。導入と保守のコストが小さく(一括付与・チェックは SPEC の適合条件とパス存在確認に限定)、`resource` 方式は現行の文書だけを対象にして誤検出を避けられている。ただし、効果(観点1・3)は未検証のため、上記の再評価のタイミングで改めて判断する。
