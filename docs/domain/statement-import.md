## 1. 外部明細取込

### 1.1 位置づけ

金融機関ごとに異なる明細データ(CSV等)のフォーマットを共通の中間表現に正規化し、[reconciliation.md](./reconciliation.md)(残高照合)・[counterparties.md](./counterparties.md)(取引先推定)・[journal.md](./journal.md)(仕訳生成)の各ドメインロジックへ橋渡しする役割を担う。[architecture.md 12章](../architecture.md#12-起票方式外部明細取込マニュアル起票)の方針の通り、フォーマットごとの差異はハードコードではなく、宣言的なデータとして表現する**マッピング定義**(`import_mapping_definitions`、[2章](#2-マッピング定義マスタimport_mapping_definitions))で吸収する。

パース処理は「CSVの読み取り([1.3](#13-csvの読み取りreader))」と「マッピング定義に基づく変換([1.4](#14-マッピング定義データ駆動))」の2段階に分離する。パースからレビュー確定までの処理フローも本ドメインで定義する。重複防止(突合)も本ドメインの取込処理の一部として行う([1.6](#16-重複防止フロー)参照)。

### 1.2 中間表現(ImportedRecord)

取込フォーマットごとの差異(列の並び、日付形式、「入金額・出金額」2列形式か「金額」1列符号付き形式か等)は、[1.4](#14-マッピング定義データ駆動)のマッピング定義が吸収し、以下の共通フォーマットに正規化して返す。

| フィールド           | 内容        | 備考                                                                                                                                                     |
| --------------- | --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `entry_date`    | 取引日       |                                                                                                                                                        |
| `description`   | 摘要        | 生文字列、正規化前。[counterparties.md 1.3](./counterparties.md#13-外部明細取込との関係)の取引先推定はここから行う                                                                    |
| `amount`        | 金額        | 符号付き整数。正 = 対象科目(手順1で選んだ口座/カード)の残高が増える方向、負 = 減る方向。CSVの正負が逆の定義は、マッピング定義の`invert_amount_sign`で反転した後の符号がここに入る([2.1](#21-フィールド))。「増える方向」が借方/貸方どちらに対応するかはこの時点では決めない([1.5](#15-レコード処理フロー)参照)                                             |
| `balance_after` | 取引後残高     | 任意。CSVに残高列がある場合のみ。[reconciliation.md 1.5](./reconciliation.md#15-残高照合)の残高照合・[1.6](./reconciliation.md#16-原因不明差異への残高調整)の残高調整に使う                         |
| `external_id`   | 外部取引の一意キー | 任意。金融機関側にIDがあれば使用。無ければレビュー確定時に`entry_date`/`amount`/`description`から正規化ハッシュを生成し代替する(具体的なアルゴリズムは[1.6](#16-重複防止フロー)、[reconciliation.md 1.3](./reconciliation.md#13-データモデルの考え方)参照)       |
| `is_settled`    | 確定済みか     | 任意(Boolean、NULL許容)。CSVの中身を解析して判定するのではなく、[1.4](#14-マッピング定義データ駆動)のマッピングに使った`import_mapping_definitions.is_settled`をそのまま引き継ぐ。確定/未確定の区別を持たないフォーマットでは`NULL` |

`amount`の符号は「対象科目の残高が増えたか減ったか」だけを表現する。複式仕訳としての借方/貸方への変換は[1.5](#15-レコード処理フロー)のレビュー確定時に行う。中間表現の段階では複式簿記の概念(借方/貸方)を持ち込まない。

> **「増える方向」は科目区分によって借方/貸方が逆転する**
> 対象科目が`asset`(銀行口座等)なら、残高が増える方向(`amount`正)は**借方**の増加。対象科目が`liability`(クレジットカード専用未払金)なら、残高が増える方向(`amount`正)は**貸方**の増加になる([financial-statements.md 2.1 生成方式](./financial-statements.md#21-生成方式)の残高計算の一般式: `asset`/`expense`は借方が増加側、`liability`/`equity`/`revenue`は貸方が増加側、と同じロジック)。この変換はマッピング定義の責務ではなく、対象科目の`category`を知っている側([1.5](#15-レコード処理フロー)のレビュー確定〜`JournalEntryRepository`)が行う。マッピング定義は「`amount`正 = 対象科目の残高が増える方向」という区分に依存しない統一ルールでCSVの生の符号表記(入金/出金列の別、プラスマイナスの意味等、フォーマットごとに異なる)を正規化する責務だけを負う。

**`ImportedRecord`の各フィールドは、確定後どこに格納されるか**

レビュー確定([1.5](#15-レコード処理フロー)の手順6〜7)で、`ImportedRecord`の内容は「編集可能な仕訳」と「不変のスナップショット」の2箇所に分かれて書き込まれる。

| `ImportedRecord`のフィールド | 編集可能な側(仕訳、後から変更しうる) | 不変のスナップショット側([reconciliation.md 2.1](./reconciliation.md#21-フィールド定義)の`external_transaction_refs`) |
|---|---|---|
| `entry_date` | `journal_entries.entry_date` | `external_transaction_refs.entry_date` |
| `description` | `journal_entries.memo`(レビュー画面での初期値、ユーザーが上書き可) | `external_transaction_refs.description` |
| `amount` | `journal_lines.amount`/`side`(科目区分に応じて借方/貸方に変換、上記「増える方向」注記参照) | `external_transaction_refs.amount`(符号付きのまま複写) |
| `balance_after` | ― | `external_transaction_refs.external_balance_after` |
| `external_id` | ― | `external_transaction_refs.external_id` |
| `is_settled` | ― | `external_transaction_refs.is_settled` |

編集可能な側は[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の通りレビュー確定後もユーザーが自由に書き換えられるのに対し、スナップショット側は書き込まれた後は不変(更新用のUI・APIを持たない)。この2つが揃って初めて、事後編集で内容が変わったかどうかを比較できる([reconciliation.md 2.1 なぜコピーを持つか](./reconciliation.md#21-フィールド定義)参照)。

### 1.3 CSVの読み取り(Reader)

CSV文字列を「行×列」の生データ(セル値の文字列の二次元配列)に変換する処理。文字コード(UTF-8/Shift-JIS等)・区切り文字(カンマ/タブ等)・改行コードの違いを吸収する構文レベルの読み取りのみを担い、各列が何を意味するか(日付か金額か等)の解釈は行わない。

- 日本の金融機関CSVはShift-JISエンコーディングが多いため、エンコーディングは[2章](#2-マッピング定義マスタimport_mapping_definitions)のマッピング定義側(`encoding`)で指定する。
  > **例外: ドラフト生成時のエンコーディング自動判定**
  > 上記の「エンコーディングは明示的に指定する(自動判定しない)」原則には、1つだけ例外がある。まだマッピング定義が存在しない「新規マッピング定義を作成する」フローでは、サンプルCSVの生バイト列から`inferEncoding`(`src/domain/statement-import/inferEncoding.ts`)がエンコーディングを推測し、ドラフトの初期値として提示する。これはまだ定義が存在しないドラフト生成時のブートストラップ用途に限定した例外であり、保存された定義は引き続き明示的な`encoding`値を持つ。定義が既に存在する通常のインポート時には、この自動判定を毎回行うことはない。
- CSVの構文解析(クォート・エスケープ等)自体は標準的なライブラリに委ね、本ドメインの対象外とする。
- CSVパース処理自体はメインスレッドで実行する([architecture.md 12章](../architecture.md#12-起票方式外部明細取込マニュアル起票)の方針を踏襲)。
- 将来TSVやExcel(.xlsx)のような別の表形式に対応する場合も、この層(生データの読み取り方法)だけを差し替えれば[1.4](#14-マッピング定義データ駆動)のマッピング定義の仕組みをそのまま再利用できる。PDF・API連携のような表形式でない入力は本ドメインの対象外とし、必要になった時点で別途検討する。

### 1.4 マッピング定義(データ駆動)

[1.3](#13-csvの読み取りreader)で得た「行×列」データを、[2章](#2-マッピング定義マスタimport_mapping_definitions)の`import_mapping_definitions`に基づいて`ImportedRecord`の配列へ変換する。マッピング定義は「どの列がどのフィールドに対応するか」「日付の書式」「金額の符号規則」等を宣言的なデータとして表現したものである。これにより、コードを書かずに新しい金融機関・フォーマットへ対応できる。

> **なぜコードではなくデータで表現するか**
> Local-first・OSSという前提([architecture.md 1章](../architecture.md#1-目的とスコープ))では、対応金融機関を増やす作業がTypeScriptを書けるコントリビューターに限られると裾野が狭くなる。マッピング定義は宣言的なデータに限定し、変換ロジック(式やコード)をデータとして持たせることは行わない。これは任意コード実行の経路を作らないためでもある([architecture.md 11章](../architecture.md#11-セキュリティプライバシー方針)のサプライチェーンリスク方針と整合)。

- 取込データの列構成が定義と一致しない場合(必須列が無い等)はマッピング処理がエラーを返す。[1.5](#15-レコード処理フロー)手順1の通り、全候補定義それぞれに実際の変換処理(読み取り→マッピング)を試み、CSVに合う候補だけに絞り込む。これは列名パターンマッチ等のヒューリスティックな「ファイルの中身からの推測」とは性質が異なり、実際に変換が成立するかどうかという事実に基づく絞り込みである。成功した候補が1件のみなら自動的にその定義が使われ、2件以上ある場合に限り、最終的にどの定義を使うかをユーザーが`label`を手がかりに明示的に選ぶ。1件も成功しない場合は、一致するフォーマットが見つからない旨をユーザーに伝える。
- **一部の行だけ読み取れない場合は、定義の保存も取込も妨げない**(計画Issue #151)。為替レートの補足行・ETC利用区間の補足行のように、日付や金額が空・不正な行が混じるCSVがある。1行でも読み取れないことを理由に、定義を保存できない・CSV全体が一致しない、とはしない。指定した列がCSVに見つからない場合と、読み取れる行が1行も無い場合(日付の書式が合わない等)だけを、保存・一致の対象外とする。読み取れない行は取り込み対象から外し(`buildStatementImportReview`の`unreadableRows`)、明細取込画面の「取り込まない行」に行番号・元のセル・理由(日付・金額)を示す。保存・一致の条件は「列が見つかり、読み取れる行が1行以上ある」だけである。読み取れない行の方が読み取れる行より多いときは、保存も取込も止めず、マッピング(列の割り当てや日付の書式)が合っているかの確認を促す警告を、明細取込画面・作成ダイアログ・マスタの「明細マッピング」タブに出す。複数の候補が通るときは、読み取れない行が最も少ない候補だけを残す(日付の書式違いなどで読めない行が多い別の定義を除く。確定明細と速報明細のように列が同じ定義は、数が同じなので残り、`label`で選ぶ)。見出しだけでデータ行が無いCSVは、列が見つかれば一致する。
- [1.2](#12-中間表現importedrecord)の`ImportedRecord.is_settled`は、マッピングに使った`import_mapping_definitions.is_settled`をそのまま引き継ぐ(個々のレコードの内容を解析して判定するのではない)。

### 1.5 レコード処理フロー

外部明細取込からレビュー確定までは、以下の順で各ドメインのロジックを通す。

1. **CSVファイルの選択、マッピング定義の絞り込み、取込先(対象科目)の確定**: 明細取込画面で、ユーザーがCSVファイルを選ぶ(計画Issue #151で、対象科目を最初に選ぶ順序から、CSVを先に選ぶ順序に改めた)。全マッピング定義(`ImportMappingDefinitionRepository.findAll`)それぞれに対して実際に[1.3](#13-csvの読み取りreader)の読み取り→[1.4](#14-マッピング定義データ駆動)の変換を試み、エラーなく成功した候補だけに絞り込む。成功した候補が1件のみならその定義を自動的に使い、楽天カードの速報用/確定用のように列構成が同一で複数候補がエラーなく成立する場合は`label`でユーザーに選ばせる。1件も成功しなければ一致するフォーマットが見つからない旨を伝え、そのCSVを元に画面内のダイアログで定義を新規作成して続けて取り込める(`inferEncoding`・`inferMappingDefinitionDraft`による下書き、[2.3](#23-組み込み定義とユーザー定義))。定義が決まったら、取込先(`asset`の口座、または`liability`のクレカ専用未払金、[accounts.md 4章](./accounts.md#4-資産負債収益費用の統合登録フロー計画issue-102)参照)を決める。取込先は画面に常に表示し、変更できる。定義に紐づく科目(取込先に選べるもの)が1つのときだけ、それを自動で取込先にする。複数の科目に紐づく定義(同じ形式のカード2枚など)では、CSVの中身から取込先を区別できず、先頭を自動で選ぶと取り違えるため、取込先を自動で決めず、ユーザーに選ばせる(選ぶまで一覧を出さない。2026-11-18。以前は先頭を初期値にしていた)。確定ボタンには科目名を入れる。どの科目にも紐づかない定義(組み込み定義の初回の利用など)では、取込先を選ぶまで一覧を出さない。取込先を変えると、重複・似た取引の候補・残高照合は取込先ごとに行うため一覧を作り直す。選ばれた定義による`ImportedRecord`の配列を以降のステップで使う。ここで決まった取込先が、以降の全ステップの`account_id`になる
2. **重複防止**: [1.6 重複防止フロー](#16-重複防止フロー)を適用する。`external_id`(またはハッシュ)の完全一致に加え、クレジットカードの速報/確定対策として日付・金額が近い既存明細の候補提示も含む
3. **残高照合**: `balance_after`が取得できる場合、[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)で帳簿残高と外部残高を照合する
4. **取引先推定**: `description`を正規化し、[counterparties.md 1.3](./counterparties.md#13-外部明細取込との関係)の部分一致パターンマッチングを適用する
5. **相手勘定科目のサジェスト**(優先順位順、[1.7](#17-相手勘定科目サジェストの範囲)参照):

   - c. どちらにも該当しなければサジェストなし。ユーザーが手動で選択する

   > マッチしなかった明細に対して1件ずつ手動選択を強いる従来のフローの負担を軽減するための、レビュー画面側のUX上の対応であり、データモデル(`keyword_rules`(旧`counterparty_patterns`))への変更は不要である。ユーザーが手動確定すると、いずれにせよ[counterparties.md 1.3](./counterparties.md#13-外部明細取込との関係)の学習によりキーワードが登録されるため、次回以降は自動マッチの対象が増えていく。

   > **取引先の設定と、ほかの行への適用(計画Issue #207)**
   > 取引先を選んだ行(推定と違う取引先を選んだ行)の取引先セルに「取引先の設定」のリンクを出し、ポップアップで取引先のキーワード(登録済み・新規)の編集・削除・追加と、キーワードごとの科目の変更ができる([counterparties.md 1.3・1.4](./counterparties.md#13-外部明細取込との関係))。変更は操作した時点でDBに保存する(登録済みの削除は押した時点、編集と、「+ キーワードを追加」で足した新規のキーワードの追加は入力を終えたとき、キーワードの科目は選んだ時点)。例外として、その行の摘要から自動で入る提案(「新規」)だけは、その行を確定したときに登録する(手順6の確定)。提案の科目欄はロックしない(2026-11-18。以前は行の相手科目が使われ変えられなかった)。科目を選ぶまでは、提案の科目は行の相手科目を初期値として追従し、選んだ後は、行の相手科目を変えてもキーワード側の科目は変わらない。確定時は、その提案の科目でキーワードを登録する。科目の選択欄は、科目グループ表示つきの選択ツリーである(従来は平らな選択欄)。ダイアログで科目を選ぶと、ダイアログを開いた行の相手科目にも反映する(手で選んだ科目でも置き換える。摘要の提案・登録済み・入力中のキーワードのすべてが対象)。ただし、下記の資産・負債の科目のキーワード設定(kind=account)の提案だけは、従来どおり対象の科目に固定する。ポップアップには、確定時に登録される旨の注記は出さない(「+ キーワードを追加」で足したキーワードは入力を終えた時点で保存済みのため)。保存の失敗はポップアップ内に出し、入力した内容は残す。保存済みの変更は、取込を破棄しても戻らない(マスタ画面と同じ扱い)。摘要の提案を、摘要に含まれない文字列などの不正な状態に直したまま確定しようとしたときは、確定せずにその旨を出して止める(消すか直すと確定できる)。
   >
   > ポップアップの「ほかの行にも適用」は、取り込み中のほかの行へ、画面上だけで反映する(この操作ではDBに書かない)。取引先は、一覧に出ているキーワード(登録済み・摘要の提案・入力中のもの)のどれか1つでも摘要(正規化後)に含み、取引先が未設定で手で触っていない行にだけ設定する。別の取引先に自動マッチした行、手で選んだ行、候補が複数あって決まらなかった行(曖昧は自動確定しない)、確定済みの行、重複で対象外の行は変えない。相手科目は、その取引先を持ち、相手科目を手で選んでいない行にだけ初期値を入れる。反映した行は初期状態(推定した取引先と相手科目)も合わせて更新し、未保存の警告の誤検知と、確定時の二重のキーワード登録を避ける。反映の取り消しはない。
   >
   > ポップアップでキーワードの科目を変えた時点で、そのキーワードに一致し、その取引先を持ち相手科目を手で選んでいない行(「ほかの行にも適用」で反映済みの行を含む)の相手科目は、「ほかの行にも適用」を押さなくても新しい科目に変わる(画面上だけ。DBへはキーワードの科目の保存のみ)。この追従は、変えたキーワードに一致する行だけで、手で選んだ科目は変えない。変えた行があれば、ポップアップに「N行の相手科目をキーワードの科目にしました」と示す(変えた行が無いときは何も出さず、直前の「ほかの行にも適用」の結果のメッセージも消す)。
   >
   > **資産・負債の相手科目のキーワードの設定(計画Issue #219)**: 取引先を持たず、相手科目が資産・負債の行には、相手科目セルの下に「キーワードの設定」のリンクを出す(取引先の設定と同じ部品。収益・費用の行には出さない)。押すと「キーワードの設定: 〈科目〉」のポップアップが開き、その科目を相手科目に指定したキーワード(登録済み)と、摘要の提案(新規)を並べる。科目はポップアップの対象の科目に固定なので、行ごとの科目の選択欄は出さない(取引先の設定の提案の科目は、2026-11-18から選べるが、この資産・負債の科目の設定だけは固定のまま)。登録済みの削除は押した時点、編集と新規の追加は入力を終えたときに保存する。摘要の提案は、相手科目を手で選んだ行にだけ出し、その行を確定したときにその科目のキーワードとして登録する(消すと登録しない。以前は確定時に黙って登録していた)。「ほかの行にも適用」は、キーワードを含み、取引先が無く、相手科目が未設定で手で触っていない行にだけ、その科目を画面上だけで入れる(別の科目が推定された行・手で選んだ行・確定済みの行・重複の行は変えない)。
   > 取引先の追加ダイアログ(取引先セルの「+ 取引先を新規追加」)では、取引先名・取引先グループ・キーワードをまとめて設定でき、「追加」を押した時点で保存する。キーワードは、キーワードごとに科目を選ぶ「キーワードと科目のセット」で入力する(最初のキーワードは行の摘要と行の相手科目。追加したキーワードの科目は、最初は指定なし)。科目の選択肢には「+ 科目を新規追加」があり、登録した科目はそのまま選ばれる(科目登録の区分の既定は「費用」。相手科目の追加でも同じで、取込先の追加は従来どおり「資産」)。「ほかの行にも適用する」のチェック(既定ON)がONのまま追加すると、ダイアログのキーワードのどれかを摘要(正規化後)に含み、取引先が未設定で手で触っていない行にだけ、取引先とキーワードの科目を画面上だけで反映する(DBには書かない。反映の条件・初期状態の更新は上記の「ほかの行にも適用」と同じ)。OFFなら追加した行だけに取引先が入る。取引先は作れてもキーワードの保存に失敗したときは、取引先は追加したうえで、保存できなかったキーワードがあることを知らせる。
   > **キーワード登録の改善(計画Issue #236、2026-11-21)**: (1) 摘要にマッチしないキーワードも、エラーにせず登録できる。含む行が0行の新規キーワードには、注意「現在の明細の摘要とはマッチしないキーワードです。」を出す(登録済みのキーワードには出さない)。(2) 取引先の追加ダイアログの取引先名の初期値に、行の摘要が入る(摘要が空なら空のままで、取引先名は必須)。(3) 新しいキーワードの科目の初期値は、その取引先のキーワードで最も多く使われている費用・収益の科目(同数なら指定なし)。(4) 複数のキーワードが一致した行の判定は、2026-11-22から長さではなく包含関係で行う(計画Issue #260。下記)。曖昧な行は自動では割り当てず、この行の取引先欄を開くと、一致した候補が先頭に並び、その下に標準のマスタ表示が続く。候補の並びは、一致したキーワードが長い順 → 過去の使用件数(取引先ごとの仕訳明細の数)が多い順 → 名前の五十音順。選ぶまで割り当てない。
   > **複数キーワードの判定と、曖昧な行の候補(計画Issue #260、2026-11-22)**: 一致したキーワードのうち最長のものが、他に一致したすべてのキーワードを(正規化後の文字列として)含むときは、より具体的なルールとして、その取引先・科目を自動で入れる(AMAZON PRIME ⊃ AMAZON)。採用したルールが持たない方は空のままにし、短いルールから補わない(決定12)。互いに包含しない独立したキーワードが重なったときは、すべて同じ取引先・同じ科目に解決される場合だけその結果を入れ、そうでなければ曖昧とし、取引先・相手科目とも自動では入れない。取引先を持たない(科目だけの)ルールが最長のときに取引先が黙って空になる、ということはなくなる(曖昧として扱う)。曖昧な行は、取引先の選択欄に加え、相手科目の選択欄でも、一致した候補を先頭に「この摘要に一致した候補」として並べる(取引先は、一致したキーワードが長い順 → 過去の使用件数が多い順 → 名前の五十音順。科目は、一致したキーワードが長い順 → 科目名の五十音順)。選ぶまで割り当てない。曖昧な行は相手科目が未選択なので、取引先欄は隠れず、取引先も科目も選べる(取引先欄が隠れるのは、相手科目に資産・負債を選んだあと)。候補が残っている行には、取引先・科目のキーワードの「ほかの行にも適用」も値を入れない(曖昧は自動確定しない)。
7. **永続化**: 確定した内容を`JournalEntryRepository`に渡し、[journal.md 1.3 貸借バランスの検証](./journal.md#13-貸借バランスの検証)を経て`journal_entries`(`source_type = 'external_import'`、[journal.md 1.7](./journal.md#17-作成経路source_type)参照)・`journal_lines`・`external_transaction_refs`を同一トランザクションで書き込む。レビュー画面でレコードごとに精算バッチとコメントを設定でき、`buildConfirmedJournalEntryInput`が仕訳を組み立てる際、選ばれた精算バッチの`settlement_batch_id`を相手科目の行にだけ付与し(口座側の行には付けない)、タグ集計方式([settlement.md](./settlement.md)参照)で対応関係を表現する。精算バッチは相手科目が割勘の一時勘定であるシステム管理の未収金(精算バッチ)・未払金(精算バッチ)のときだけ選択でき(計画Issue #151。Repository側の検証も計画Issue #167で同じ範囲に揃えた、[settlement.md 1.7](./settlement.md#17-タグ付き一時勘定の消込settlement_batch_idによるタグ付け))、相手科目がそれ以外になると選択はクリアされる。この2科目は、システム管理の科目を除く相手科目の候補にも含める。仕訳の摘要`journal_entries.memo`には、CSVの摘要を標準化した形(`formatDescriptionForDisplay`: NFKC、空白の連続を1つに、カタカナにつづくハイフン・ダッシュ類を長音「ー」に)で保存する。突合用記録`external_transaction_refs.description`と外部取引IDはCSVの値のまま(取込済み判定が崩れないように)。キーワードの照合用の正規化(`normalizeDescriptionForMatching`)にも同じハイフンの処理を加えた(2026-11-18。取り込み済みの既存の仕訳の摘要はスキーマv4の差分で変換した)。コメントは`journal_entries.comment`に設定し、空白のみは未設定として扱う(計画Issue #144)。

   > **手順5-aのサジェストは未実装(計画Issue #144時点)**

> **複数CSVの一括取込(計画Issue #214)**
> 同じ形式のCSVは、まとめて選んで1回のレビューで確定できる。入口は仕訳画面の「明細から起票」で、押すと明細取込画面(開始状態)へ移る。CSV(複数選択可)は、その明細取込画面の「CSVを選択」で選ぶ(計画Issue #231。以前は仕訳画面でCSVを選び、メモリ上の受け渡し口(`pendingImportFiles`)で渡していたが、開始状態にある一時保存の一覧([1.9](#19-一時保存と再開計画issue-231-フェーズ3))へ着けないため、遷移だけにして受け渡し口を廃した)。未保存の警告は、ボタンを押した時点で出す(ファイルを選ぶ前に移るため)。
>
> - **共通のマッピング定義**: ファイルごとに手順1の実パース試行を行い、より多くのファイルを読める定義だけを候補にする(`resolveMultiFileMappingCandidates`)。その定義で読めないファイルは、全体を止めずに「取り込めなかったファイル」として理由(見つからない列)つきで示し、残りで続ける。読めるファイル数が同じ定義が複数あれば、手順1どおり表示名で選ぶ。取込先の科目はファイルごとには変えられず、1つだけ選ぶ(同じ形式のカード複数枚の取り違えを防ぐため)。
> - **取り込むファイルの選択**: 読めたファイルは期間(最も早い取引日)の早い順に一覧し、各ファイルをチェックで外せる。外したファイルは最初から選ばなかったものとして扱い、重複判定・件数・残高照合は残ったファイルだけで行う。チェックを変えると一覧を作り直すが、入力済みの内容は外部取引IDで引き継ぐ(未保存の警告は出さない。2026-11-18。以前は警告を通していた)。外したファイルの行の入力も覚えておき、戻すと復元する。CSVの選び直し・取込先の変更では、覚えた入力を破棄する。
> - **連結**: 2ファイル以上のときは、取引日の昇順に並べる(同じ日の中は、ファイルの順・CSVの行の順を保つ)。1ファイルのときは従来どおりCSVの並びのままで、「ファイル」列・ファイルの一覧は出さない。「取り込まない行」(読み取れない行)は、どのファイルの何行目かを示す。
> - **ファイル間の重複**: [1.6](#16-重複防止フロー)参照。重複行は「ファイル『…』の同じ明細と重複のため対象外です」と示し、「重複元の行へ移動」で重複元の行へスクロールして強調する。重複元の行からも重複した行へ移れる。取込済み(`external_transaction_refs`)との完全一致の行には、画面を離れずに既存の仕訳の内容を開く「取り込み済みの仕訳を見る」を付ける(別画面へ移ると未保存の警告が出るため)。

### 1.6 重複防止フロー

`is_reconcilable`の値によらず、外部明細の取込対象として選ばれた科目であればすべて適用される独立した処理である([reconciliation.md 1.1 用語: 突合と照合](./reconciliation.md#11-位置づけ)参照)。

1. CSVをパースし、各行について`external_id`(またはハッシュ)を算出する
2. 同一`account_id` × `external_id`の組み合わせが`external_transaction_refs`に既に存在するか判定する(完全一致)
3. 完全一致すれば「取込済みの可能性」として明細取込画面で警告し、既定では取り込まない。ユーザーが明示的に選択した場合のみ取り込みを許可する(意図的な再取込や、ハッシュ衝突などの誤検知を救済するため)。計画Issue #151の画面では、その行は入力欄も選択も出さず「取り込み済みのため対象外です」と表示し、行内の「取り込む」を押した場合だけ新規として扱う(`includeDuplicate`)。取り込むにした行は、同じ位置の「取り込まない」で元の「対象外」に戻せる(誤って押したときの取り消し)。ファイル間の重複行も同じ
4. 完全一致しない場合でも、同一`account_id`内に日付が3日以内・金額が3%以内の既存の仕訳があれば、「似た取引」として候補を提示する(クレジットカードの速報→確定で内容が変わるケースや、手入力との二重計上への対処、詳細は次項)。候補の探索対象には、突合マスタを持つ仕訳に加えて、突合マスタを持たない手入力(`manual`)・定期取引生成(`recurring_generated`)の仕訳も含める(計画Issue #145。手入力した取引のCSVを後から取り込んだときの二重計上に気づくため)。初期残高・残高調整・割勘・外部明細取込の仕訳は、突合マスタが無くても含めない(「置き換える」を選ぶと候補が削除され、残高照合や精算の土台が壊れるため)
5. いずれにも該当しなければ重複ではないとして扱い、[1.5](#15-レコード処理フロー)の手順3以降(残高照合・取引先推定・相手勘定科目のサジェスト・永続化)に進む。未消込の未払金・未収金がある場合の消込仕訳としてのサジェスト・作成は[1.5](#15-レコード処理フロー)の手順5a・手順7で扱う内容であり、ここでは重複判定の結果のみを扱う

> **正規化ハッシュのアルゴリズムと同一バッチ内完全一致レコードへの対応**
> `external_id`が無い場合、`entry_date`/`description`/`amount`を結合した文字列から**djb2**(Daniel J. Bernsteinによる軽量な非暗号学的文字列ハッシュ)で正規化ハッシュを生成し代替する。Web Crypto(`SubtleCrypto`)のような暗号学的ハッシュ関数は採用しない。暗号強度は不要であり(ハッシュ衝突による誤検知は本節(3)の通りユーザーが明示的に選択して救済する設計を既に前提にしている)、`SubtleCrypto`の非同期APIは重複判定ロジックを同期的な純粋関数としてテストする方針と相性が悪いためである。
>
> ハッシュ化はレコード単体ではなく、取込対象のCSV1回分(バッチ)全体の`ImportedRecord[]`を入力に取る。同一バッチ内に`entry_date`/`description`/`amount`が完全一致するレコードが複数存在する場合(例: 同じコンビニで同じ商品を同日中に2回購入)、レコード単体からハッシュ化すると同一の`external_id`が生成され、[2.1 フィールド定義](./reconciliation.md#21-フィールド定義)の`UNIQUE(account_id, external_id)`制約に違反してしまう。これを避けるため、完全一致するレコード群にはバッチ内での出現順インデックスをハッシュの入力に混ぜ込み、区別できるようにする。

> **複数ファイルのハッシュと、ファイル間の重複(計画Issue #214)**
> 複数CSVを連結して1バッチとして`resolveExternalIds`を呼ぶと、期間が重なるファイルで同日・同額・同摘要の明細が連番化し(出現順インデックスが全体で通し番号になる)、重なった分が「新規」と誤判定されて二重計上する。そのため、外部取引IDの代替ハッシュは**ファイル単位**で算出する(`buildMultiFileStatementImportReview`)。ファイルを期間(最も早い取引日)の早い順に処理し、同じ外部取引IDが先のファイルに既にあれば、後のファイルの行を「ファイル間の重複」とする(先のファイルの行を残す。選択順には依存しない)。ファイル単位で出現順インデックスを振るため、同じファイル内の正当な同日・同額・同摘要の複数明細は落とさず、重なる分だけが重複になる。
>
> ファイル間の重複行は取込済みの完全一致と同じ扱い(`isExactDuplicate`)で、既定では取り込まず、利用者が明示した場合だけ取り込める。取り込む場合に`UNIQUE(account_id, external_id)`に当たらないよう、重複行の外部取引IDは元のIDに`#file-dup-N`を付けた別の値にする。これにより、のちに同じファイルを単独で取り込み直したときは、元のIDが取込済みと一致して重複として扱われる。

> **メモ: 候補選定ロジックの方向性**
> 候補の対象科目は`account_id`で既に固定されているため、複雑なsubset-sum探索は不要で、起票日・取引日が近いものを候補として提示するだけで大半のケースは収まる見込み。具体的には、未消込エントリが1件のみ(家賃・給与等)ならそのまま提示、複数件ある(クレジットカード等)場合は日付が近いものから合計額を突き合わせて絞り込む、という単純な方式で足りると考えられる。厳密な一致探索(組み合わせ最適化)は過剰であり、合わない場合は無理に自動一致させず[settlement.md 1.2](./settlement.md#12-家賃給与の例)の通り差額を残したまま消込を許容すればよい。

**確定版候補のサジェストと置き換え(クレジットカードの速報/確定対策)**

クレジットカードの明細は、速報時点と確定後で金額・摘要が変わることがある(海外利用時の為替確定、高速道路料金の後日確定等)。`external_id`(またはハッシュ)による完全一致だけに頼ると、確定後の再取込が「別の取引」として扱われ二重計上されてしまう。

そこで(4)の通り、完全一致しなくても同一`account_id`内で日付・金額が近い既存の仕訳があれば「似た取引」として候補を提示する。候補が付いた行には「似た取引が登録済みです。二重ではありませんか?」と警告し、次の3つから扱いを選ばせる。既定は「別の取引なので追加する」で、警告を見落として確定すると、登録済みの仕訳を残したまま二重に登録される(運用でカバーする。完全一致の重複防止は従来どおり働く)。

| 選択肢 | 処理 |
|---|---|
| 別の取引なので追加する(既定) | 登録済みの仕訳を残したまま、この取引を新規で保存する |
| 同じ取引なので、登録済みを削除して置き換える | 登録済みの仕訳を1件削除し、確定後の内容でこの取引を保存する。[reconciliation.md 1.4 ライフサイクル](./reconciliation.md#14-ライフサイクル)の「削除して正しい内容で再取込」パターンをそのまま使う。候補が手入力の仕訳でも同じ。候補が複数あるときは、削除する1件を利用者が選ぶ(選ぶまで確定できない。誤って別の仕訳を消さないよう、全件削除はしない)。手入力の仕訳には`is_settled`がないため、候補の並び順は`is_settled`が未取得の既存明細と同じ扱いになる |
| この取引を保存しない | この行を取り込まない(登録済みの仕訳をそのまま使う)。行はグレーになり、選び直すまで編集できず、一括設定・キーワードの適用の対象にもならない。確定の件数・残高照合の見込みにも含めない |

**候補の探索と割り当て**: 近似判定は、取り込み済みとの完全一致(重複)の行には行わない。1件の既存の仕訳は、金額差・日付差が最も小さい1行にだけ紐づける(1対1。`assignApproximateDuplicateCandidates`)。同じ金額の取引が続くCSV(毎日のコーヒーなど)で、1件の登録済みの仕訳に複数の行から警告が出たり、同じ仕訳を複数の行から「置き換え」ようとして二重に削除したりするのを防ぐため。1行に複数の既存の仕訳が紐づく場合は、`is_settled = false`、金額差の小さい順、日付差の小さい順に並べ、画面には最も近い1件だけを出して残りは「ほか N 件を見る」で開く。

**一覧の並び**: 取り込んだ行は「重複」→「似た取引あり」→「問題なし」の3グループに分けて並べる(グループの中は取り込んだ順)。分類は取り込んだときの内容で決まり、操作しても行は動かない。保存時の並び(`rowOrder`)は元のCSVの順を使う。

**グループの折りたたみ(計画Issue #231 フェーズ1)**: 3グループの見出しは開閉のボタンで、折りたたむとそのグループの行は描画しない(初期状態はすべて開く)。折りたたんでも、全選択・一括操作・確定の対象は変わらない。見出しには、件数と「未確認 N件」(相手科目が決まっていない行の数)を折りたたみ中も出す。重複元の行・重複した行への移動は、移動先のグループが折りたたまれていれば自動で開く。開閉の状態は、取り込むファイルのチェックの切り替えと、一部だけ確定して残りを続けるときは保ち、CSVの選び直し・取込先の変更では初期状態に戻す。行が0件のグループは見出しごと出さない。

**入力済み/未入力の色分けとヘッダーでの並び替え(計画Issue #231 フェーズ2)**: 相手科目が決まっている行(ステータスが「新規」)は薄い緑、未入力の行は従来の背景にする。状態の文字に、入力済みは✓、未入力は破線の丸を添えて、色だけに頼らない。「似た取引あり」の行は、入力済みになると直下の確認の行とまとめて緑になる。重複・「この取引を保存しない」の行は色分けの対象外。ヘッダー(取込ファイル(複数ファイルのとき)・日付・摘要・金額・相手科目・取引先・状態)を押すと、グループの中だけが 昇順 → 降順 → 解除(取り込んだ順)で並び替わる。プロジェクト・メンバー・コメント・チェックの列は並び替えない。並びは押した時点の値で決まり、行に入力しても動かない(押した時点に無かった行と、未設定の値は最後)。保存時の並び(`rowOrder`)は、いつも元のCSVの順。並び替えの状態は折りたたみと同じ寿命で、ファイルのチェックの切り替えと、一部だけ確定して続けるときは保ち、CSVの選び直し・取込先の変更では解除する。

近似判定の閾値は、レビュー画面の既定値として**日付が3日以内・金額が取込側の金額の3%以内**とする(計画Issue #219の続き。以前は14日・1,000円で、ほぼ全行に警告が出て実用にならなかったため絞った)。このため、速報と確定で3%を超えて動く取引(為替の確定など)は候補にならない。ドメインとしては閾値を規定せず、呼び出し側が渡す。

`external_transaction_refs.is_settled`([reconciliation.md 2.1](./reconciliation.md#21-フィールド定義)参照)が取得できる場合、`is_settled = false`の既存明細を優先的に確定版候補として提示する。未確定と分かっている明細ほど、後から確定版に置き換わる可能性が高い。`is_settled`が判定できない金融機関(大多数)では、日付・金額の近さのみで候補を提示する。

> **なぜ自動で置き換えないか**
> 本ケース(重複判定の自動化)は、[1.7](#17-相手勘定科目サジェストの範囲)で類似度推定を見送った判断とは、外れた場合のコストが非対称である点で異なる。取引先サジェストが外れても手動選択の手間が増えるだけだが、重複判定を誤って自動処理すると、別の取引を誤って削除する、あるいは二重計上を見逃す、というデータ整合性上の実害が生じる。したがって候補は提示するが、確定は常にユーザーのレビューを必須とする([architecture.md 12章](../architecture.md#12-起票方式外部明細取込マニュアル起票)の一貫方針)。

> **確定版が来なかった場合**
> `is_settled = false`のまま新しいCSVが来ず、確定版に置き換わらない状態を許容する。検知・催促の仕組みは特に持たない。クレジットカードの明細であれば、いずれ未払金の消込([settlement.md](./settlement.md)、[journal.md 1.2](./journal.md#12-記帳の型具体例)参照)の対象になるため、確定額とズレていればその消込時の複合仕訳で気づける。

### 1.7 相手勘定科目サジェストの範囲

キーワードルールによる取引先・科目の推定([1.5](#15-レコード処理フロー)の4・5-b。取引先経由の既定の科目は廃止した)のみをMVPスコープとする。取引先が特定できない場合、過去の類似摘要文字列からの推定のような追加のサジェスト機構は持たず、ユーザーに手動選択させる。

> **なぜ類似摘要からの推定を見送るか**
> 類似度判定(表記ゆれ・部分一致の閾値調整等)の設計・実装コストに対して、MVPで得られる精度向上の恩恵が見合わない。[counterparties.md 1.3](./counterparties.md#13-外部明細取込との関係)の学習の仕組み(手動確定した摘要が`pattern`として自動登録される)により、取引先マスタが育つにつれて自然にサジェスト精度は上がっていくため、初手から複雑な推定ロジックを持ち込む必要性が薄い。

### 1.8 複合仕訳への対応

[counterparties.md 1.2](./counterparties.md#12-紐づけ対象)で触れた「クレジットカード引き落とし明細を複合仕訳(未払金消込)にまとめる」運用は、明細の取り込み粒度([1.5](#15-レコード処理フロー)の5-a)の話であり、マッピング定義側が複数のCSV行を1仕訳に束ねる特別な処理を持つわけではない。1件のCSVレコード(=1回の口座引き落とし)に対して、レビュー画面で複数の未消込未払金を選択し複合仕訳として消し込む、という形で表現する([settlement.md](./settlement.md)の複合仕訳の考え方と同じ)。

### 1.9 一時保存と再開(計画Issue #231 フェーズ3)

件数が多いCSVは、1回の作業で全行の相手科目・取引先を入力しきれない。そこで、取込作業を途中で中断し、後から続きを再開できるようにする。確定は従来どおり(失敗した行を残して他の行を確定する継続処理方式、[1.5](#15-レコード処理フロー)手順7)で、一時保存は「確定しない入力を、CSVごと取っておく」ための仕組みである。journal_entry_drafts([journal.md](./journal.md) 3章、1仕訳ごとの途中保存)とは別物で、`external_transaction_refs`と結びつかず、重複判定には効かない(確定済みの行は、再開時に重複として自動で除外される)ため流用しない。

**保存するもの**(DDLは[docs/schema/statement_import.sql](../schema/statement_import.sql)の`statement_import_drafts`・`statement_import_draft_files`):

- CSVの生データ(取り込んだ全ファイルを選んだ順に。バイト列のまま)、取り込むファイルのチェック
- マッピング定義(id)、取込先の科目、「誰の明細か」(取込先の科目に名義があるときは持たない)
- 行ごとの入力: 初期値(キーワードルールによる推定など)から変えた行だけを、外部取引IDをキーに持つ(`isRowEdited`と同じ考え方。確定済みの行は含めない)。保存する項目は、取引先・相手科目(手で選んだか)・プロジェクト・世帯メンバー・精算バッチ・コメント・「取り込む」(重複)・似た取引の扱いと置き換える仕訳・摘要の提案(キーワード登録)の入力。推定の記録(初期の取引先・取引先の候補)は、再開時に計算し直すので含めない
- 開始状態の一覧に出す、保存時点の全件数と、そのうち投入できた(相手科目が決まっている)件数、保存日時

重複判定・似た取引の候補・残高照合の結果は保存しない。**保存する入力は参照先(科目・取引先など)に外部キーを張れないJSON**なので、再開時に存在を検証する。折りたたみ・並び替え([1.6](#16-重複防止フロー)「一覧の並び」)の状態も保存せず、再開時は初期状態(すべて開く・取り込んだ順)になる。

**保存数と上書き**: 一時保存は取込先の科目ごとに1つ(DDLの`UNIQUE`)。同じ取込先に保存し直すと上書きする(idと作成日時は保つ)。再開した一時保存への保存は確認なしで上書きし、別の取込から同じ取込先に保存しようとするときは「上書きしますか」の確認を出す。

**保存の操作**: 取込画面の一覧が出ているとき、画面上部のボタン列と確定ボタンの横に「一時保存」を出す。押すと保存して通知を出し、画面はそのまま続けられる(確定はしない)。保存した状態と同じ行は、未保存の編集とみなさない(保存後に他の画面へ移るときは、未保存の警告を出さない。そのあとに入力を変えると出る)。

**未保存の警告**: 警告のダイアログに、「保存して移動」(入力済みの行を確定し、確定できない行は一時保存してから移動する。全行を確定できたときは一時保存を作らず、再開していた一時保存は削除する)と、「一時保存して移動」(何も確定せず、すべての入力を一時保存してから移動する)を出す。確定の前提(誰の明細か・摘要の提案の検証)を満たせず確定できないときは、何も保存せず移動しない。「破棄して移動」は何も保存しない。

**再開**: 取込画面の開始状態(CSVを選ぶ前)に一時保存の一覧(取込先・CSV・入力済み/全件・保存日時)を出し、「再開」でCSVを選び直さずに一覧を開く。保存したCSVを、保存時のマッピング定義で読み直し、重複判定・似た取引の候補・残高照合を**いまの帳簿で計算し直して**、その初期値の上に保存した入力を重ねる。利用者の入力は、キーワードルールの自動推定より優先する。保存のあとに確定した行は、取込済みとの完全一致として重複(対象外)になる。取込先・取り込むファイルのチェック・「誰の明細か」も戻す。再開した直後は、再開したこと・いまの帳簿で計算し直したことを通知する。
- 保存してから、科目・取引先・プロジェクト・世帯メンバー・精算バッチが削除(無効化)されていたり、「置き換える」の対象の仕訳が候補に無くなっていたりする入力は戻さず、その項目を初期値に戻す。戻せなかった行の数を橙色の通知で伝える(行のほかの入力は戻す)。
- 保存時のマッピング定義が削除・編集されて、保存したCSVを読み取れないときは、一覧を開かず、既存の「一致する定義が無い」と同じ形の案内を出す(CSVと入力は一時保存に残る)。「このCSVでマッピングを新規作成」で定義を作り直すと、保存した取込先・入力を戻して続けられ、「一時保存を破棄」で削除できる。
- 取込先の科目が削除されたときは、一時保存も一緒に消える(`ON DELETE CASCADE`)。マッピング定義・名義の世帯メンバーが削除されたときは、一時保存は残り、その参照だけが外れる(`ON DELETE SET NULL`)。

**後始末**: 全行を確定したとき、再開していた一時保存を、CSVの生データごと削除する(CSVがDBに残らない)。一部しか確定できないときは残す。開始状態の一覧の「破棄」(確認のあと)でも削除する。別の取込(再開していない)が全行を確定しても、同じ取込先の古い一時保存は消さない(利用者が破棄を選ぶ)。

**履歴に残さない**: 一時保存の保存・削除は、操作履歴(ロールバック、計画Issue #202)に記録しない(`OperationHistory.untracked`)。取り消す意味が無く、CSVの生データを含む取消用のSQLを履歴のメモリに持たせないため。確定のグループの途中で書いても、確定の操作に混ざらない。

**懸念と限界**: 銀行明細のCSVが、確定・破棄されるまでDBに残る(DBサイズが増え、バックアップ・同期フォルダにも含まれる)。確定・破棄で必ず消えること、再開した一時保存は確定の後始末で消えることを、テストで保証している。

### 2.3 組み込み定義とユーザー定義

定義と科目の紐づけは多対多で、**制限ではなく優先順位**として扱う(計画Issue #151)。取込先の科目に紐づく定義があれば候補の先頭に並べ、紐づく定義がなければ全定義から選べる。ある科目に紐づいた定義は、紐づいていない別の科目の取込でも選べる。実際にパースが成立した候補が1つなら自動で選び、複数なら`label`で選ばせる([1.5](#15-レコード処理フロー)手順1)。OSSとして主要金融機関向けの定義がアプリに同梱される想定であり([3章 責務分担](#3-責務分担)参照)、これらはどの科目にも紐づかない汎用の定義として提供される。取込先の科目に対して定義を選んで取り込みを確定すると(`StatementImportScreen`が確定後に`linkAccount`を呼ぶ)、その科目との紐づけを自動で追加し、次回から候補の先頭に出る。

紐づけの入口は2つある(計画Issue #189)。データの正は中間テーブル`import_mapping_definition_accounts`の1箇所で、どちらの入口も同じテーブルを読み書きし、一方の操作は他方の画面を再表示すると見える。(1)マスタの「明細マッピング」タブ: 定義の編集で対応する科目を差し替える(`update`の`accountIds`)。(2)マスタの「勘定科目」タブ: 外部明細がある資産・負債の科目の右パネルで、その科目への紐づけ・解除を即時に行う(`linkAccount`・`unlinkAccount`。科目単位で、他の科目の紐づけには触れない)。あわせて、科目の新規登録フォーム(マスタ・取込画面共通)で、外部明細ありと答えた資産・負債に限り、登録と同時に定義を紐づけられる。紐づけ先になれる科目(マッピングタブの「対応する科目」の選択肢)と明細取込の取込先は、外部明細がある科目(`accounts.has_external_statement`、未記録の行は照合可否から推定)だけに限る。科目マスタからは紐づけと解除までで、定義の新規作成・CSVからの作成は「明細マッピング」タブの責務のまま。解除により組み込み定義が「どの科目にも紐づかない汎用の定義」に戻っても、既存の仕様どおり問題ない。

計画Issue #76で、楽天カード(確定明細/速報明細)・楽天銀行・PayPayカード(確定明細)の組み込み定義を`src/infrastructure/db/builtInMappingDefinitions.ts`に実装し、`seedBuiltInMappingDefinitions`がWorker起動時(`runMigrations`直後)に冪等投入するようにした(`format_group_id`・`is_settled`の組み合わせで既存定義との重複を判定し、ユーザーが編集・独自作成した定義があれば再投入しない。計画Issue #151で、科目に紐づけ済みの定義も含めて判定するようにした。紐づけ後の再起動で組み込み定義が重複して増えるのを防ぐため)。列構成・日付形式・エンコーディングは実際のCSVサンプルから確認した値を使用しているが、楽天カードのCSVは末尾に日付列が空の特殊行(未確定明細のキャンセル区分、確定明細のETC利用区間補足行等)を含むことがあり、[1.4](#14-マッピング定義データ駆動)の変換処理では日付を読み取れない行になる。計画Issue #151以降は、その行を取り込み対象から外して「取り込まない行」に示すだけで、CSVを加工せずに取り込める(従来は、利用者がその範囲を除いてアップロードする必要があった。詳細は`docs/guides/knowledge.md`)。ユーザー自身が定義を作成・編集する画面は、計画Issue #151でマスタの「明細マッピング」タブに追加した(表示名・金融機関の識別子・明細の種類・対応する科目・文字コード・区切り文字・見出しまでの行数・日付の書式・金額の形式・各列の割り当てを編集でき、選んだCSVの元データと取り込み結果を並べてプレビューする。プレビューは実際の取込と同じ変換`mapRowToImportedRecord`を行単位で使い、読み取れない行は理由を行ごとに示す。プレビュー用のCSVは保存しない。CSVからの新規作成では`inferEncoding`・`inferMappingDefinitionDraft`で下書きを作る)。組み込み定義も編集・削除でき、編集しても`seedBuiltInMappingDefinitions`は同じ組み合わせの定義が存在する限り再投入しない。

> **削除・更新にライフサイクル制約を設けない理由**
> `accounts`や`projects`と異なり、`import_mapping_definitions`は仕訳や`external_transaction_refs`から直接参照されない。マッピング定義は取込実行時にのみ使われる一時的な変換ルールであり、取込済みの仕訳データは定義への参照を保持しない。したがって定義を削除・変更しても過去の取込結果には影響せず、[accounts.md 2章](./accounts.md#2-勘定科目のライフサイクル)のような「紐づく仕訳があれば削除不可」という保護は不要である。
>
> 逆方向として、口座/カード自体([accounts.md 2章](./accounts.md#2-勘定科目のライフサイクル)の物理削除、仕訳が0件の場合のみ可能)が削除された場合、その科目との紐づけだけが消え(`import_mapping_definition_accounts`の`ON DELETE CASCADE`)、定義は残る(自動では削除しない)。

## 3. 責務分担

外部明細取込に関わる4層の責務を明確に分離する。

| 層 | 責務 | 持たない責務 |
|---|---|---|
| CSVの読み取り(Reader、[1.3](#13-csvの読み取りreader)) | CSV文字列 → 「行×列」の生データへの変換のみ。文字コード・区切り文字の差異を吸収 | 列の意味(日付か金額か等)の解釈は行わない |
| マッピング定義(`import_mapping_definitions`、[2章](#2-マッピング定義マスタimport_mapping_definitions)) | 「行×列」データ → `ImportedRecord`への変換。列の意味・日付書式・金額の符号規則を宣言的なデータとして保持 | 変換ロジック(コード・式)は持たない。重複判定・取引先推定・複式簿記への変換は一切行わない |
| 明細取込画面 | 複数CSVの共通定義の判定結果・取り込めなかったファイルの表示、重複・取り込み漏れの警告表示、相手科目のサジェスト提示、ユーザーによる確認・修正の受付([1.5](#15-レコード処理フロー)の2〜6) | 最終的なドメインルールの強制(貸借バランス等)は行わない。CSVを選ぶ前は画面中央に「CSVを選択」ボタンを出し、取り込んだ行を編集中に他画面へ移る・新しいCSVを選ぶときは、未保存の警告を出す(`isRowEdited`、推定した初期値のままなら出さない。計画Issue #193、`docs/decisions.md` 2026-11-14) |
| `JournalEntryRepository` | 確定した仕訳ドラフトの永続化、貸借バランス検証([journal.md 1.3](./journal.md#13-貸借バランスの検証))、[1.6](#16-重複防止フロー)の重複防止(突合)に必要な`external_transaction_refs`の作成 | 外部明細取込固有の知識(読み取り・マッピング・サジェスト)は持たない。マニュアル起票と共通の入り口([architecture.md 12章](../architecture.md#12-起票方式外部明細取込マニュアル起票)) |

この分担により、「入力経路(外部明細取込かマニュアルか)によってドメインの整合性ルールが分岐しない」という[architecture.md 12章](../architecture.md#12-起票方式外部明細取込マニュアル起票)の方針が保たれる。読み取り・マッピングとレビュー画面はあくまで`JournalEntryRepository`への入力を組み立てる前段階であり、最終的な整合性は常に`JournalEntryRepository`が一元的に担保する。

マッピング定義は宣言的なデータであり、コードを書かずに追加できる。OSSとして、新しい金融機関・フォーマットへの対応はマッピング定義の追加(コミュニティによるコントリビューション)を主な想定経路とする。CSVの読み取り(Reader)側は文字コード・区切り文字といった構文レベルの差異のみを扱うため、拡張の主戦場にはならない。
