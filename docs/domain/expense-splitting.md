# 経費按分(割勘)ドメイン

[domain.md](../domain.md)(エントリポイント)から分割された、複数人で分担する支出の割勘(按分)に関する詳細設計。

> **関連ドメイン**
> 一時勘定を経由した消込という会計処理の基本形は[settlement.md](./settlement.md)で定義されている。本ドメインはその応用として、世帯メンバー間・世帯外の相手との間で発生する立替・精算を扱う。新しいマスタテーブルは持たず、既存の`accounts`・`projects`・`household_members`・`counterparties`・`journal_entry_links`の組み合わせで表現する。

## 1. 割勘

### 1.1 位置づけ

割勘とは、複数人で分担すべき支出を、後から本来の負担者に按分し直す会計処理を指す。[settlement.md](./settlement.md)の消込(暫定計上した一時勘定をCSV到着後の実際の入出金と対応付けて解消する処理)とは性質が異なり、割勘は「誰が誰にいくら立て替えたか」という**新しい経済的事実**が発生する処理である。したがって元の仕訳(消込を含む)を書き換えたり打ち消したりはせず、常に追加の仕訳として積む。

> **なぜ元仕訳に触れないか**
> 元仕訳(カード利用明細等)は既に消込([settlement.md](./settlement.md))を経ていることが多く、外部の実際の入出金と対応している。割勘によって発覚するのは「実はこの支出の一部はBさんの負担だった」という後から判明した事実であり、過去の記録の訂正ではない。[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の「日常的な入力ミスの訂正」とは性質が異なるため、直接編集や反対仕訳ではなく、元仕訳・消込仕訳を一切変更しない追加の仕訳(割勘・精算)として表現する。

### 1.2 一時勘定(立替金)

割勘は、精算が済むまでの間だけ立替額を保持する一時勘定を経由する。[settlement.md 1.4 一時勘定はis_reconcilable = falseで登録する](./settlement.md#14-一時勘定はis_reconcilable--falseで登録する)と同じ考え方で、`is_reconcilable = false`の資産・負債科目として登録する([accounts.md 1.2 区分(5要素)](./accounts.md#12-区分5要素)に例示されている「立替金」がこれにあたる)。

| 科目 | 区分 | 役割 |
|---|---|---|
| 立替金(資産) | asset | 自分が立て替えた分の債権 |
| 立替金(負債) | liability | 自分が立て替えてもらった分の債務 |

**科目自体は割勘のたびに新規作成しない。** 恒久的な汎用科目として1組だけ用意し、以降のすべての割勘で使い回す。「誰の債権/債務か」は`journal_lines.household_member_id`([household-members.md 1.2](./household-members.md#12-紐づけ対象と既定値の継承)、全区分に適用可)、「どの割勘バッチに属する残高か」は`journal_lines.project_id`([projects.md 1.2](./projects.md#12-紐づけ対象)、全区分に適用可)で区別する。

> **なぜ人・バッチごとに専用科目を作らないか**
> 検討の初期段階では「未収入金(Aさん)」「未払金(Bさん)」のように人ごとの専用科目や、割勘バッチごとの一時的な科目を都度作成する案も検討したが、いずれも使い捨ての科目で科目一覧が肥大化する。プロジェクト(`project_id`)を「どのバッチか」を表すタグとして使えば、科目自体は`household_member_id`と組み合わせた汎用の2科目だけで足りる。割勘バッチには「26/7生活費割勘」のような名前で`kind = 'settlement'`のプロジェクトを作成する([projects.md 1.5 種別(kind)](./projects.md#15-種別kind)参照)。精算が終わり立替金の残高が0になると、[projects.md 1.3 ライフサイクル](./projects.md#13-ライフサイクル)の通り非アクティブ化がユーザーに提案される。これは`project_id`をPL科目限定からBSを含む全区分へ拡張した主要な動機でもある([projects.md 1.2 なぜBSにも許可するか](./projects.md#12-紐づけ対象)参照)。

### 1.3 世帯メンバー間の割勘

割勘相手が世帯メンバー(このアプリの家計簿に自分の口座を持つ人)の場合、立替金の資産側・負債側の両方を使う。

```
例: Aさんのカードで1,000円の食事(本来はA・B折半)をし、後からBさんに500円分を割り勘する

元仕訳(カード利用):    (借) 費用・食費(A)            1,000
                       (貸) 負債・カード未払金               1,000

消込(口座引落):        (借) 負債・カード未払金        1,000
                       (貸) 資産・口座(A)                   1,000

割勘:                  (借) 費用・食費(B)              500
                       (借) 資産・立替金                500   household_member_id=A, project_id=26/7生活費割勘
                       (貸) 費用・食費(A)                     500
                       (貸) 負債・立替金                      500   household_member_id=B, project_id=26/7生活費割勘

精算1(Bさんの口座CSV): (借) 負債・立替金               500   household_member_id=B, project_id=26/7生活費割勘
                       (貸) 資産・口座(B)                    500

精算2(Aさんの口座CSV): (借) 資産・口座(A)              500
                       (貸) 資産・立替金                     500   household_member_id=A, project_id=26/7生活費割勘
```

割勘entryは「食費をAからBへ付け替える」行と「立替金の債権・債務を発生させる」行の2組4行から成る、単一の仕訳として貸借が均衡する。精算1・精算2をあえて分けているのは、AさんとBさんの銀行振込が別々のタイミング・別々のCSVで到着するため([reconciliation.md](./reconciliation.md)の突合は口座ごとに独立して行われる)。

### 1.4 世帯外の相手との割勘

割勘相手がこのアプリの家計簿に口座を持たない相手(友人など)の場合、相手側の負債は家計簿の管理範囲外になるため、立替金の資産側だけを使う。相手は[counterparties.md](./counterparties.md)の取引先として登録し、「誰からの精算待ちか」を取引先軸で追跡する。

```
例: Aさんのカードで1,000円の食事(本来は友人Bさんと折半)をし、Bさんから500円を受け取る予定

元仕訳(カード利用):     (借) 費用・食費(A)             1,000
                        (貸) 負債・カード未払金               1,000

消込(口座引落):         (借) 負債・カード未払金         1,000
                        (貸) 資産・口座(A)                    1,000

割勘:                   (借) 資産・立替金                500   household_member_id=A, project_id=26/7生活費割勘
                        (貸) 費用・食費(A)                     500   counterparty_id=友人Bさん

精算1(友人からの振込):  (借) 資産・口座(A)              500
                        (貸) 資産・立替金                     500   household_member_id=A, project_id=26/7生活費割勘
```

負債側の立替金は発生しない(友人自身の負債を家計簿で管理する意味がないため)。`counterparty_id`は食費(A)の行(PL科目)にのみ設定でき、立替金の行(BS科目)には設定できない([counterparties.md 1.2 紐づけ対象](./counterparties.md#12-紐づけ対象)の通りPL限定のまま変更しない)。

### 1.5 割勘の履歴と取り消し

**履歴の閲覧**: 割勘entryは元entryに対して`journal_entry_links`の`allocates`リンクを持つ([journal.md 1.8 仕訳間の関係](./journal.md#18-仕訳間の関係journal_entry_links)参照)。元entryの詳細画面から`to_entry_id = 元entry AND link_type = 'allocates'`で割勘entryを辿り、さらに`to_entry_id = 割勘entry AND link_type = 'settles'`で精算entryを辿れば、「元の支出 → 割勘 → 精算」の一連の流れを追跡できる。また、`project_id`でバッチ全体の仕訳を横断的に一覧することもできる([projects.md 1.4 集計への影響](./projects.md#14-集計への影響)参照)。

**取り消し**: 割勘entry・精算entryはいずれも通常の手入力仕訳(`source_type = 'manual'`)であり、[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の既存ルール(物理削除は常に許可)がそのまま適用される。

- **精算前の取り消し**: 割勘entryを物理削除すれば元に戻る。`ON DELETE CASCADE`で`allocates`リンクも消え、元entryは最初から変更していないため実質的に「なかったこと」になる
- **精算後の取り消し**: 割勘entry・精算entryを削除すれば帳簿上は取り消せるが、精算で実際に現金がAさん・Bさん間(または友人との間)で移動していた場合、削除だけでは口座残高と実態がズレる。この場合は現実の返金を行い、それを新しい取引として記録する必要がある。これはどんな会計処理でも避けられない制約であり、割勘固有の問題ではない

専用の「取り消し」機能や、逆仕訳・非表示フラグのような特別な仕組みは不要で、既存の物理削除ルールに乗るだけで要件を満たす。

### 1.6 他ドメインへの影響

- [accounts.md 1.2 区分(5要素)](./accounts.md#12-区分5要素): 「立替金」を割勘専用の恒久的な一時勘定として位置づける
- [projects.md 1.2 紐づけ対象](./projects.md#12-紐づけ対象): `project_id`をPL限定から全区分へ拡張した主要な動機。割勘バッチの識別に使う
- [projects.md 1.5 種別(kind)](./projects.md#15-種別kind): `kind`区分(`settlement`/`event`)を導入する主要な動機の1つ。割勘バッチは`kind = 'settlement'`として作成し、立替金の精算残高が0になった時点で非アクティブ化が提案される
- [journal.md 1.8 仕訳間の関係](./journal.md#18-仕訳間の関係journal_entry_links): `journal_entry_links`に`allocates`リンク種別を追加する主要な動機
- [counterparties.md](./counterparties.md): 世帯外の相手を取引先として扱う([1.4](#14-世帯外の相手との割勘)参照)
- [statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)手順5-a: 立替金は`is_reconcilable = false`の通常科目のため、既存の未消込サジェスト機能がそのまま働く。割勘専用のインポートロジックは持たない
