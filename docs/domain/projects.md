## 1. プロジェクト

### 1.1 位置づけ

プロジェクトは「何の目的で使ったお金か」を表す軸であり、勘定科目(用途)・取引先(支払先)とは直交する。[domain.md 1.1](../domain.md#11-基本方針)の方針の通り、勘定科目の階層に混ぜ込まず、独立したエンティティとして持つ。

「26年7月アメリカ旅行」のように期間や目的が明確な催しに紐づく支出を横断的に集計したい、という要求に応える機能。勘定科目を細分化する(例:「旅行用食費」を新設する)のではなく、既存の勘定科目(食費・交通費など)はそのまま使い、プロジェクトという軸で横串を刺す。

### 1.2 紐づけ対象

プロジェクトは仕訳明細(JournalLine)単位で紐づける。1つの仕訳(複合仕訳)の中でも、行ごとに異なるプロジェクトを設定できる。

```
例: 1回のカード決済でお土産(旅行用)とスーツケース(日用品)を同時に購入

(借) 費用・お土産代    5,000   project = 26年7月アメリカ旅行
(借) 費用・日用品費    3,000   project = (なし)
(貸) 負債・未払金             8,000
```

プロジェクトは**全区分(資産・負債・純資産・収益・費用)の行に設定可能**とする。[household-members.md 1.2](./household-members.md#12-紐づけ対象と明細行の世帯メンバーの決め方)の`household_member_id`と同じ扱いであり、区分による制限はない。

> **なぜBSにも許可するか**
> 当初はPL科目(収益・費用)限定としていた。理由は「口座残高の管理軸(BS)と支出目的の分析軸(プロジェクト)を独立させる」ことにあったが、[expense-splitting.md](./expense-splitting.md)の割勘機能の検討で見直した。割勘の立替金(資産/負債)にも元の支出が属するイベントのタグを引き継がせたい(例: 旅行中の立替をイベント別PLに正しく反映する)という要求があり、区分による制限を撤廃した([1.4](#14-集計への影響)参照)。
>
> なお、割勘の「精算バッチ」を識別するタグは`project_id`ではなく`settlement_batch_id`(計画Issue #133、[settlement.md](./settlement.md)参照)が担う。両者は`journal_lines`上の独立したカラムであり、1行が両方を同時に持てる(例: 割勘仕訳の立替金行は`settlement_batch_id`、費用の付け替え行は`project_id`を持つ)。
>
> `counterparty_id`([counterparties.md 1.2](./counterparties.md#12-紐づけ対象))は引き続きPL限定のままとする。「誰と取引したか」は口座残高そのもの(BS)には意味をなさない一方、「誰の/何の目的の資産・負債か」はBSにも意味があるため、`project_id`・`household_member_id`とは扱いが異なる。
>
> 区分による制限がなくなったため、以前必要だった専用のTRIGGER([journal.md 2.2 DDL](./journal.md#22-ddl)参照)は不要になった。

### 1.3 ライフサイクル

プロジェクトは勘定科目と同様、削除ではなく非アクティブ化を基本とする。プロジェクトはイベント専用(計画Issue #133)であり、ゼロに戻るべき残高という概念を持たないため、非アクティブ化は常にユーザーの判断によるものであり、システムからの提案は行わない(精算バッチの残高ゼロによる非アクティブ化提案は[settlement.md](./settlement.md)の`settlement_batches`側が担う)。

| 操作 | 条件 | 扱い |
|---|---|---|
| 物理削除 | 仕訳明細・定期取引ルールのいずれでも使われていない | 可 |
| 物理削除 | 上記のいずれかで使用中 | 不可(非アクティブ化のみ)。仕訳明細は`prevent_delete_project_with_journal_lines`トリガー、定期取引ルールは外部キー制約がDBレベルで拒否する(`masterDeletionConstraints.test.ts`で確認済み、計画Issue #154)。画面は事前に判定し、使用中の理由を表示する |
| 名称変更 | 常に | 可 |
| 非アクティブ化 | 任意(例: 旅行が終わった) | 過去集計はそのまま表示、新規仕訳では選択不可 |

`is_system_managed`に相当する概念(組み込みでシステムが用意し特別扱いする、あらかじめ登録済みのプロジェクト)は持たない。すべてのプロジェクトはユーザーが作成する。`kind`に相当する分類も持たない(計画Issue #133で廃止、[1.4](#14-集計への影響)参照)。

### 1.4 集計への影響

[financial-statements.md 2章 財務諸表(FS)](./financial-statements.md#2-財務諸表fs)の期間集計とは独立した軸として、「プロジェクト別の集計」を提供する。[1.2](#12-紐づけ対象)の通り全区分に`project_id`を設定できるため、PL(収益・費用の累計)だけでなくBS(資産・負債の残高)も同じ軸で集計できる。

```
プロジェクト別科目残高(区分ごとに増加側が異なる、financial-statements.md 2.1の一般式と同じ) =
  区分がasset/expenseなら Σ(amount WHERE side = 'debit') - Σ(amount WHERE side = 'credit')
  区分がliability/equity/revenueなら Σ(amount WHERE side = 'credit') - Σ(amount WHERE side = 'debit')
  (project_id = 対象プロジェクト、期間で絞らず全期間が既定)
```

費用・収益科目については従来通り「プロジェクト別の支出合計」として使える。資産・負債科目については「このプロジェクトに紐づく残高」を表示できるが、精算バッチ(割勘の立替金・未払金の残高をゼロへ近づけていく管理)は`settlement_batches`が専用に担う(計画Issue #133、[settlement.md](./settlement.md)参照)。

期間PL([financial-statements.md 2章](./financial-statements.md#2-財務諸表fs))は「特定の期間の全支出」を、プロジェクト別集計は「特定の目的の全体(期間不問が既定)」を表す。両者は互いに独立した2つの切り口として併存する。両方を同時に絞り込む(例:「今月のアメリカ旅行費用」)ことも、期間条件とproject_id条件を組み合わせるだけで自然に実現できる。

## 2. プロジェクトマスタ(projects)

### 2.1 フィールド定義

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `id` | プロジェクトID | PK |
| `name` | プロジェクト名 | 例:「26年7月アメリカ旅行」、自由記述 |
| `project_group_id` | 表示用グループ | FK(`project_groups`)、任意。単一所属。NULL=未分類(計画Issue #143) |
| `sort_order` | 表示順 | 同じ入れ物(同一`project_group_id`)の中での表示順。表示専用 |
| `is_active` | アクティブ/非アクティブ | falseにしても過去仕訳・過去集計に影響なし |
| `created_at` | 作成日時 | |
| `updated_at` | 更新日時 | |

**project_groups**(計画Issue #143)

「旅行全部」のようにまとめて絞り込めるよう、勘定科目グループ([accounts.md 3.3](./accounts.md#33-勘定科目グループマスタaccount_groups))と同じ仕様のグループを持つ。種類ごとの表として新設し(共通テーブル案・タグ(多対多)案は不採用)、集計ロジックには一切関与しない表示専用のラベルである。

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `id` | グループID | PK |
| `name` | グループ名 | 同じ親グループ内でユニーク(非アクティブは除外) |
| `parent_group_id` | 親グループ | FK(自己参照)、任意。NULL=最上位。循環参照になる親変更はRepository層で拒否する |
| `sort_order` | 表示順 | 同じ入れ物の中での表示順。サブグループと直属のプロジェクトで1つの表示順を共有する |
| `is_active` | 有効/非アクティブ | |
| `created_at` / `updated_at` | 作成・更新日時 | |

子グループまたは所属するプロジェクトがあるグループは物理削除できない(トリガーで強制)。`category`は持たない。

勘定科目マスタと異なり、`is_reconcilable`・`is_system_managed`に相当するフィールドは持たない([1.3 ライフサイクル](#13-ライフサイクル)参照)。`kind`も持たない(計画Issue #133で廃止、[settlement.md](./settlement.md)の`settlement_batches`へ分離)。
