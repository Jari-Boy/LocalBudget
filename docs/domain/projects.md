## 1. プロジェクト

### 1.1 位置づけ

プロジェクトは「何の目的で使ったお金か」を表す軸であり、勘定科目(用途)・取引先(支払先)とは直交する。[domain.md 1.1](../domain.md#11-基本方針)の方針の通り、勘定科目の階層に混ぜ込まず、独立したエンティティとして持つ。

「26年7月アメリカ旅行」のように期間や目的が明確な催しに紐づく支出を横断的に集計したい、という要求に応える機能。勘定科目を細分化する(例:「旅行用食費」を新設する)のではなく、既存の勘定科目(食費・交通費など)はそのまま使い、プロジェクトという軸で横串を刺す。

### 1.2 紐づけ対象

プロジェクトは仕訳明細(JournalLine)単位で紐づける。1つの仕訳(複合仕訳)の中でも、行ごとに異なるプロジェクトを設定できる。

```
例: 1回のカード決済でお土産(旅行用)とスーツケース(日用品)を同時に購入

(借) 費用・お土産代    5,000   project = 26年7月アメリカ旅行
(借) 費用・日用品費    3,000   project = (なし)
(貸) 負債・未払金             8,000
```

プロジェクトは**全区分(資産・負債・純資産・収益・費用)の行に設定可能**とする。[household-members.md 1.2](./household-members.md#12-紐づけ対象と既定値の継承)の`household_member_id`と同じ扱いであり、区分による制限はない。

> **なぜBSにも許可するか**
> 当初はPL科目(収益・費用)限定としていた。理由は「口座残高の管理軸(BS)と支出目的の分析軸(プロジェクト)を独立させる」ことにあったが、[expense-splitting.md](./expense-splitting.md)の割勘機能の検討で見直した。割勘は「立替金」という汎用の一時勘定(資産/負債)を複数の割勘バッチで使い回し、`project_id`でどのバッチに属する残高かを区別する設計になっている([expense-splitting.md 1.2](./expense-splitting.md#12-一時勘定立替金)参照)。これにより「プロジェクト別の資産・負債」(例:立替金の未精算残高)も見えるようになり、プロジェクト別の集計がPLだけでなく簡易的なBSも持てるようになる([1.4](#14-集計への影響)参照)という実利もある。
>
> `counterparty_id`([counterparties.md 1.2](./counterparties.md#12-紐づけ対象))は引き続きPL限定のままとする。「誰と取引したか」は口座残高そのもの(BS)には意味をなさない一方、「誰の/何の目的の資産・負債か」はBSにも意味があるため、`project_id`・`household_member_id`とは扱いが異なる。
>
> 区分による制限がなくなったため、以前必要だった専用のTRIGGER([journal.md 2.2 DDL](./journal.md#22-ddl)参照)は不要になった。

### 1.3 ライフサイクル

プロジェクトは勘定科目と同様、削除ではなく非アクティブ化を基本とする。

| 操作 | 条件 | 扱い |
|---|---|---|
| 物理削除 | 紐づく仕訳明細が0件 | 可 |
| 物理削除 | 紐づく仕訳明細が1件以上 | 不可(非アクティブ化のみ) |
| 名称変更 | 常に | 可 |
| 非アクティブ化 | 任意(例: 旅行が終わった) | 過去集計はそのまま表示、新規仕訳では選択不可 |
| 非アクティブ化の提案 | `kind = 'settlement'`のプロジェクトで、精算残高(いずれも[1.5](#15-種別kind)参照)が0に達した | システムは自動で非アクティブ化せず、「非アクティブ化しますか?」とユーザーに提案するに留める |

> **なぜ精算残高0到達時に自動で非アクティブ化しないか**
> [recurring-transactions.md 1.6 ライフサイクル](./recurring-transactions.md#16-ライフサイクル)の`max_occurrences`到達時と同じ判断。システムが完了を検知できても`is_active`を自動で変更すると、「ユーザーが意図して非アクティブ化したのか」「システムが自動的に判定したのか」をUI上で区別できなくなる。非アクティブ化はあくまでユーザーの操作として残し、システムは「精算残高が0になりました」という気づきのきっかけ(提案)だけを提供する。

`is_system_managed`に相当する概念(組み込みでシステムが用意し特別扱いする、あらかじめ登録済みのプロジェクト)は持たない。すべてのプロジェクトはユーザーが作成する。

一方、[1.5 種別(kind)](#15-種別kind)の通り、「プロジェクトがどう使われるか」を区別する軽量な分類は`kind`として持つ。詳細は[1.5](#15-種別kind)を参照。

### 1.4 集計への影響

[financial-statements.md 2章 財務諸表(FS)](./financial-statements.md#2-財務諸表fs)の期間集計とは独立した軸として、「プロジェクト別の集計」を提供する。[1.2](#12-紐づけ対象)の通り全区分に`project_id`を設定できるため、PL(収益・費用の累計)だけでなくBS(資産・負債の残高)も同じ軸で集計できる。

```
プロジェクト別科目残高(区分ごとに増加側が異なる、financial-statements.md 2.1の一般式と同じ) =
  区分がasset/expenseなら Σ(amount WHERE side = 'debit') - Σ(amount WHERE side = 'credit')
  区分がliability/equity/revenueなら Σ(amount WHERE side = 'credit') - Σ(amount WHERE side = 'debit')
  (project_id = 対象プロジェクト、期間で絞らず全期間が既定)
```

費用・収益科目については従来通り「プロジェクト別の支出合計」として使える。資産・負債科目については「このプロジェクトに紐づく残高(例: 割勘バッチの未精算の立替金)」を表示できる([expense-splitting.md](./expense-splitting.md)参照)。

期間PL([financial-statements.md 2章](./financial-statements.md#2-財務諸表fs))は「特定の期間の全支出」を、プロジェクト別集計は「特定の目的の全体(期間不問が既定)」を表す。両者は互いに独立した2つの切り口として併存する。両方を同時に絞り込む(例:「今月のアメリカ旅行費用」)ことも、期間条件とproject_id条件を組み合わせるだけで自然に実現できる。

### 1.5 種別(kind)

プロジェクトの使われ方は大きく2種類に分かれる。

| `kind` | 内容 | 例 |
|---|---|---|
| `settlement`(精算バッチ) | 一時勘定(資産・負債)の残高を最終的にゼロへ近づけていくことを目的とするバッチ。[settlement.md 1.7](./settlement.md#17-タグ付き一時勘定の消込project_idhousehold_member_idの引き継ぎ)の分割払い、[expense-splitting.md 1.2](./expense-splitting.md#12-一時勘定立替金)の割勘バッチ、家族・友人間の貸し借りなど | 「スマホ24回払い」「26/7生活費割勘」「妹への貸付」 |
| `event`(イベント) | 特定の期間・目的の収支を横断的に集計したいだけで、ゼロに戻るべき残高という概念を持たない | 「26年7月アメリカ旅行」 |

**精算残高の定義**: `kind = 'settlement'`のプロジェクトが紐づく資産・負債科目それぞれについて[1.4](#14-集計への影響)の式を適用する。そのすべての科目で残高が0になった状態を精算残高と呼ぶ。通常は科目1つだけのことが多いが、[expense-splitting.md 1.3 世帯メンバー間の割勘](./expense-splitting.md#13-世帯メンバー間の割勘)のように資産側・負債側の両方の立替金を使うバッチでは、両方が0であることを要する。この精算残高が0になった時点で、[1.3 ライフサイクル](#13-ライフサイクル)の非アクティブ化提案の対象になる。

> **未記帳(紐づく資産・負債科目の仕訳明細が1件もない)場合の扱い**
> 上記の定義は「紐づく資産・負債科目」が存在することを前提としている。プロジェクト作成直後などでそのプロジェクトに紐づく資産・負債科目の仕訳明細が1件も記帳されていない場合、単純に「すべての科目で残高が0」という条件だけを見ると精算残高0(精算完了)と区別がつかなくなってしまう。そのため、紐づく資産・負債科目の仕訳明細が1件もない場合は精算残高0とはみなさず、非アクティブ化提案の対象外とする。

`kind`は、使い道が次の2点に限定されるUI上の軽量な分類である。

- プロジェクト一覧画面での種別ごとのグルーピング表示
- `kind = 'settlement'`のプロジェクトに限り、[1.3 ライフサイクル](#13-ライフサイクル)の非アクティブ化提案の対象にする(`event`のプロジェクトは対象にしない。旅行のようなイベントは支出の累計がゼロに戻ることがなく、「精算完了」という状態自体が存在しないため)

> **なぜ勘定科目の`category`と混同しないか**
> `category`は複式簿記上の借方/貸方判定に直接関与する必須の区分である。一方、`kind`は会計処理そのものには影響しない付帯情報であり、[accounts.md 1.3 グルーピング表示用](./accounts.md#13-グルーピング表示用)の`account_groups`と同様、UI上の分類・機能切り替えの位置づけにとどまる。プロジェクトが「システムに特別扱いされる」のは`kind = 'settlement'`のプロジェクトが非アクティブ化提案の対象になるという一点のみであり、削除・集計等の基本的な扱いは`kind`によらず共通のままである。

## 2. プロジェクトマスタ(projects)

### 2.1 フィールド定義

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `id` | プロジェクトID | PK |
| `name` | プロジェクト名 | 例:「26年7月アメリカ旅行」、自由記述 |
| `kind` | 種別 | ENUM: `settlement`(精算バッチ)/`event`(イベント)、既定`event`。[1.5 種別(kind)](#15-種別kind)参照 |
| `is_active` | アクティブ/非アクティブ | falseにしても過去仕訳・過去集計に影響なし |
| `created_at` | 作成日時 | |
| `updated_at` | 更新日時 | |

勘定科目マスタと異なり、`is_reconcilable`・`is_system_managed`に相当するフィールドは持たない([1.3 ライフサイクル](#13-ライフサイクル)参照)。`kind`は持つが、会計ロジックに関与しない軽量な分類である([1.5 種別(kind)](#15-種別kind)参照)。
