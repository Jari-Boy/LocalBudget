# 消込(Settlement)ドメイン

[domain.md](../domain.md)(エントリポイント)から分割された、暫定計上(未払金・未収金)とCSV到着後の消込に関する詳細設計。

> **関連ドメイン**
> 本ドメインは、暫定計上された一時勘定を、CSV到着後に実際の外部取引と対応付けて解消する「消込」という会計処理そのものを定義する。消込の対応関係は[journal.md 1.8 仕訳間の関係](./journal.md#18-仕訳間の関係journal_entry_links)の`journal_entry_links`(`link_type = 'settles'`)に記録され、サジェスト(外部明細取込時に未消込の一時勘定をサジェストする処理)は[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側で行う。一時勘定を経由する必要がある理由は[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)・[recurring-transactions.md 1.1](./recurring-transactions.md#11-位置づけ)側で扱う。

## 1. 消込

### 1.1 位置づけ

消込とは、暫定計上された一時勘定(未払金・未収金)の残高を、実際の入出金(CSV由来の仕訳)と対応付けて解消する処理を指す。1回の暫定計上に対して消込が1回で完結するとは限らず、分割払いのように複数回に分けて段階的に解消していくケースもある([1.6 分割消込](#16-分割消込消込残高による完了判定)参照)。

家賃や給与のように、実際に現金が動くタイミングではなく発生した時点で記帳したい取引は、`liability`(未払金等)、または`asset`(未収金等、ただし`is_reconcilable = false`)の一時勘定を経由して暫定計上する。CSV到着後、その一時勘定を口座科目で消し込む。

一時勘定を経由する必要がある理由(口座科目への直接記帳が制限されていること)自体は本ドメインの関心事ではなく、[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)・[recurring-transactions.md 1.1](./recurring-transactions.md#11-位置づけ)側の制約に委ねる。本ドメインが定義するのは、一時勘定が既に存在する前提で、それをどう解消するか(消込仕訳の組み方・対応関係の記録方法)である。

この形は新しい概念ではなく、[journal.md 1.2 記帳の型](./journal.md#12-記帳の型)にある「カードで買い物→後日引き落とし」の未払金パターンと同じ構造である。

### 1.2 家賃・給与の例

```
例: 家賃(費用側)

暫定計上(手入力・定期取引): (借) 費用・家賃         80,000
                          (貸) 負債・未払金               80,000

CSV到着後の消込(CSV由来): (借) 負債・未払金         80,000
                          (貸) 資産・普通預金             80,000
```

```
例: 給与(収益側)

暫定計上(手入力・定期取引): (借) 資産・未収金        300,000
                          (貸) 収益・給与収入            300,000

CSV到着後の消込(CSV由来): (借) 資産・普通預金        250,000
                          (借) 費用・社会保険料         30,000
                          (借) 費用・所得税             20,000
                          (貸) 資産・未収金                  300,000
```

> **消込は金額が一致するとは限らない**
> 給与の例のように、天引き(社会保険料・所得税等)があると暫定計上額と実際の入金額はずれる。消込は単純な1:1の仕訳ではなく[journal.md 1.1](./journal.md#11-仕訳journalentryと仕訳明細journalline)の複合仕訳として行い、差額を按分する(天引き内訳を費用科目に分解するか、単に収益科目側の金額を実額に合わせるかはユーザーの任意)。
>
> 按分しきらず未払金・未収金に残高が残ることも許容する。これは異常ではなく、見込みと実績のズレとして正常に起こりうる状態である。ドメイン側は「消込は複合仕訳として組める」という枠組みのみ提供し、按分方法そのものは規定しない。

### 1.3 クレジットカード専用未払金との違い

[accounts.md 4章 資産・負債・収益・費用の統合登録フロー](./accounts.md#4-資産負債収益費用の統合登録フロー計画issue-102)で登録するクレジットカード未払金科目は`is_reconcilable = false`である。ここまでの家賃・給与の例で使った汎用未払金・未収金と同じく、記帳経路の制限は受けない。ただし役割は異なる。汎用未払金は「口座引落を待つ暫定計上」の受け皿として使うのに対し、カード専用未払金は主に**外部明細取込(利用明細CSV)由来の仕訳を直接記帳する対象**として使う。カードの支払い方法は口座振替とは限らないため`is_reconcilable = false`とした経緯は[accounts.md 4.5 なぜis_reconcilable = falseにするか](./accounts.md#45-なぜis_reconcilable--falseにするか)を参照。

```
例: クレジットカードの利用(カード専用未払金)

利用明細CSV由来:      (借) 費用・食費                3,000
                      (貸) 負債・未払金(楽天カード)          3,000
```

利用明細CSVをそのまま取り込んで記帳するため、家賃・給与のような暫定計上は経ない。この重複防止(突合)は`is_reconcilable`の値によらず働く独立した仕組みであるため([reconciliation.md 1.1](./reconciliation.md#11-位置づけ)参照)、`is_reconcilable = false`であってもカード単位で正しく機能する。

**支払い(消込)の2つの経路**

カードの支払い方法によって、消込の記帳経路が異なる。

- **口座振替(自動引き落とし)**: 口座側のCSVを取り込んだ際に生成される消込仕訳(`source_type = 'external_import'`)が、カード未払金を減少させる。

```
  口座CSV由来の消込:    (借) 負債・未払金(楽天カード)    50,000
                      (貸) 資産・普通預金             50,000
```

  `負債・未払金(楽天カード)`と`資産・普通預金`の両方を借方/貸方に使うが、どちらも同じ1つの仕訳の`source_type`で判定されるため、科目ごとに個別の外部参照を用意する必要はない([journal.md 1.7 作成経路(source_type)](./journal.md#17-作成経路source_type)参照)。

- **コンビニ払い等(現金・外部明細を伴わない経路)**: 対応する外部明細が存在しないため、`source_type = 'manual'`で消込仕訳を手入力する。カード未払金が`is_reconcilable = false`であるからこそ、この経路が可能になる([accounts.md 4.5](./accounts.md#45-なぜis_reconcilable--falseにするか)参照)。

いずれの経路でも、消込仕訳と消し込まれる元の利用明細仕訳との対応関係は、`journal_entry_links`(`link_type = 'settles'`)に記録する([journal.md 1.8 仕訳間の関係](./journal.md#18-仕訳間の関係journal_entry_links)参照)。複数の利用明細をまとめて消し込む複合仕訳では、1件の消込仕訳から複数の元仕訳へのリンクになる。カードの利用明細に対応する`external_transaction_refs`はカード自身のCSVインポート時に作られたものがそのまま残り、消込側で新たに作る必要はない。

カードに対して残高照合が行われない理由は[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)の「対象科目」を参照。

### 1.4 一時勘定のis_reconcilable設定

`未収金`・`未払金`はCSVと直接照合されるべき本物の口座ではなく、あくまで内部の一時勘定である。そのため`is_reconcilable = false`として登録する([accounts.md](./accounts.md)参照)。`is_reconcilable = true`にしてしまうと、[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)のルールにより一時勘定自体への暫定計上(手入力)ができなくなり本末転倒になる。

### 1.5 他ドメインへの影響

- [accounts.md](./accounts.md)は、口座登録UXとは別に「一時勘定」として`is_reconcilable = false`の資産・負債科目をユーザーが作成できる必要がある([1.4](#14-一時勘定のis_reconcilable設定)参照)。
- 仕訳作成時の`journal_entry_links`(`link_type = 'settles'`)の生成は`JournalEntryRepository`の責務であり、`is_reconcilable`資産への記帳経路制限とあわせて[reconciliation.md 2.3 他ドメインへの影響](./reconciliation.md#23-他ドメインへの影響)で定義する。
- サジェスト(未消込の未払金・未収金の金額・日付の近似度等)の方法は、外部明細取込のレビュー画面側の実装課題として[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側に委ねる。本ドメインは「消込は複合仕訳として組める」という枠組みのみを規定する。「未消込」の判定基準そのものは[1.6 分割消込](#16-分割消込消込残高による完了判定)の消込残高に基づく。
- [projects.md 1.5 種別(kind)](./projects.md#15-種別kind): タグ付き一時勘定([1.7](#17-タグ付き一時勘定の消込project_idhousehold_member_idの引き継ぎ)参照)の識別に使うプロジェクトは`kind = 'settlement'`として作成する運用を前提とする。精算残高が0になった時点の非アクティブ化提案は`projects.md`側の責務であり、本ドメインは消込残高([1.6](#16-分割消込消込残高による完了判定))を通じてその判定材料を提供するだけに留める。

### 1.6 分割消込(消込残高による完了判定)

分割払い(例: スマホ本体代金を12回の口座引き落としで支払う)のように、1件の暫定計上を1回の消込では解消しきれず、複数回のCSV取込にまたがって段階的に解消していくケースがある。この節では、消込が「どこまで進んでいて、いつ完了したとみなせるか」を定義する。

**消込残高の定義**

ある元仕訳(`to_entry`)の消込残高は、次の式で求める。

```
消込残高 = 元仕訳の一時勘定科目行の金額
         - Σ(journal_entry_links.amount WHERE link_type = 'settles' AND to_entry_id = 元仕訳.id)
```

消込残高が`0`になった時点で、その一時勘定は消込完了とみなす。[journal.md 1.8](./journal.md#18-仕訳間の関係journal_entry_links)の通り`settles`は`to_entry_id`に対して一対多になりうるため、1件の元仕訳に対して`from_entry_id`の異なる複数の消込仕訳が積み重なっていく形をそのまま許容する(スキーマ上`to_entry_id`にユニーク制約は課さない)。

> **なぜ専用のステータスカラムを持たないか**
> `journal_entries`や一時勘定科目に「消込済みフラグ」のような専用カラムを追加する案も検討したが、[recurring-transactions.md 2.1](./recurring-transactions.md#21-フィールド定義)の`max_occurrences`が生成済み件数を専用カウンタではなく`journal_entries`のCOUNTから都度算出するのと同じ理由で見送る。`journal_entry_links`の`amount`を集計すれば消込残高は一意に復元できるため、フラグと実際のリンクの状態がずれる(二重管理の)リスクを避けられる。
>
> サジェスト([statement-import.md 1.5](./statement-import.md#15-レコード処理フロー)手順5-a)が対象とする「未消込」も、この消込残高が`0`より大きい元仕訳を指す。

**例: スマホ本体代金の分割払い(12回)**

```
契約時の暫定計上(手入力):     (借) 費用・通信費(端末)   120,000
                            (貸) 負債・未払金(分割)          120,000

1回目のCSV到着後の消込:      (借) 負債・未払金(分割)    10,000
                            (貸) 資産・普通預金               10,000
  → 消込残高 = 120,000 - 10,000 = 110,000(未完了)

  …(2〜11回目も同様に毎月10,000円ずつ消込)…

12回目のCSV到着後の消込:     (借) 負債・未払金(分割)    10,000
                            (貸) 資産・普通預金               10,000
  → 消込残高 = 120,000 - 120,000 = 0(消込完了)
```

12回それぞれが独立した`journal_entries`(`source_type = 'external_import'`)であり、いずれも`journal_entry_links`(`link_type = 'settles'`, `to_entry_id` = 契約時の暫定計上仕訳)を1件ずつ持つ。契約全体の残債務(いま消込残高がいくら残っているか)は、この消込残高の計算をUI表示のたびに行えばよく、[recurring-transactions.md 1.2](./recurring-transactions.md#12-自動生成-vs-レビュー確認)の見通し表示と同様、別テーブルに永続化する必要はない。

> **消込残高がマイナスになるケース(過剰消込)**
> ユーザーが誤って合計額を超えて消込仕訳を対応付けると消込残高は負になりうるが、DB制約としては禁止しない。[1.2 消込は金額が一致するとは限らない](#12-家賃給与の例)で許容している「按分しきらず残高が残る」ケースと同様、これも見込みと実績のズレとして起こりうる状態であり、訂正(消込仕訳の編集・削除)はユーザーの通常の仕訳編集操作([journal.md 1.5](./journal.md#15-仕訳の編集削除))に委ねる。ドメイン側で自動的な整合性回復は行わない。

> **「毎月分を都度計上する」代替案との使い分け**
> 分割払いは、本節のように契約時に総額を一括計上して段階的に消し込む形のほか、[recurring-transactions.md 3章 大口費用の按分](./recurring-transactions.md#3-大口費用の按分)の枠組みで「毎月分を独立した一時勘定計上として都度生成し、その都度1:1で消し込む」形でも表現できる。前者は契約全体の残債務(消込残高)を一時勘定の集計として把握したい場合に、後者は各月の計上を完全に独立させて按分・解約時の扱いを[recurring-transactions.md 3.4](./recurring-transactions.md#34-按分ルールの終了)の既存の枠組みに乗せたい場合に向く。どちらもドメインとして矛盾なく成立するため、ユーザー(またはUI)がケースに応じて選べばよく、本ドメインはどちらか一方を強制しない。

### 1.7 タグ付き一時勘定の消込(project_id・household_member_idの引き継ぎ)

一時勘定(未払金・未収金、[expense-splitting.md 1.2 一時勘定(立替金)](./expense-splitting.md#12-一時勘定立替金)の立替金も含む)を使い回す設計では、`journal_lines.project_id`([projects.md 1.2](./projects.md#12-紐づけ対象))・`household_member_id`([household-members.md 1.2](./household-members.md#12-紐づけ対象と既定値の継承))で「どの分割払い契約/どの割勘バッチの残高か」をタグ付けする。これにより、[projects.md 1.4 集計への影響](./projects.md#14-集計への影響)の行単位の集計でタグ別残高を追うことができる。このようなタグ付けに使うプロジェクトは`kind = 'settlement'`として作成する([projects.md 1.5 種別(kind)](./projects.md#15-種別kind)参照)。これにより、精算残高が0になった時点で非アクティブ化がユーザーに提案される。

このとき、消込仕訳側の一時勘定行に`to_entry`側と同じタグを付け忘れると、[1.6](#16-分割消込消込残高による完了判定)の消込残高(`journal_entry_links`ベース、entry単位)はゼロになっても、タグ別残高(`journal_lines`ベース、行単位)には未消込分が残ってしまう。これは「消込が完了したか」を判定する経路が実質2つ(entry単位の消込残高と、タグ単位の行集計)存在し、後者がユーザーのタグ入力に依存してしまっていることに起因する。

**自動化の範囲と選定の委譲**

一時勘定に紐づく未消込の`to_entry`がN件ある場合、そのうちどれを・いくらずつ今回の消込に対応させるかは、金額・日付の近似度だけから一意に決められる保証がない([statement-import.md 1.6 重複防止フロー](./statement-import.md#16-重複防止フロー)の「メモ: 候補選定ロジックの方向性」も参照)。この選定と金額配分は、既存の[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)手順5-aで元々ユーザー(レビュー画面)に委ねられている判断であり、タグの有無によって新たに発生する負担ではない。N=1の場合も本来は同じ確認が必要だが、候補が1件しかないため見た目上は自動選択に近い。

「ユーザーがどの`to_entry`をいくら消し込むかを確定させた後」であれば、その組み合わせごとの`project_id`・`household_member_id`は一意に定まる。したがって`JournalEntryRepository`が、確定した各`(to_entry, amount)`の組に対応する消込仕訳側の一時勘定行のタグを、`to_entry`側の対応行から機械的にコピーする。これによって自動化できるのは「選定が終わった後、消込仕訳側のタグを手入力し直して食い違う・入れ忘れる」という付け間違いだけである。「そもそも違う`to_entry`を選んでしまう」という選定自体の誤りは防げない。これは消込機能に限らず、あらゆる手動選択操作に共通する限界であり、本ドメインが特別に解決する対象ではない。

これにより、消込残高([1.6](#16-分割消込消込残高による完了判定))とタグ別残高([projects.md 1.4](./projects.md#14-集計への影響))という2つの独立した集計が、少なくとも「選定は合っているのにタグのコピーだけを間違える」という経路では食い違わなくなる。

**タグが異なる元仕訳をまとめて消し込む場合(1:N・N:N)**

[1.3 クレジットカード専用未払金との違い](#13-クレジットカード専用未払金との違い)のように1件の消込が複数の元仕訳を一括で消し込む場合(1:N)、[1.6](#16-分割消込消込残高による完了判定)の分割消込と組み合わされば1件の元仕訳が複数回・複数件まとめての消込を受けることもある(N:N)。いずれの場合も、元仕訳ごとにタグ(どの分割払い契約か・どの割勘バッチか)が異なることがある。

原則は単純で、**`journal_entry_links`の1行(`from_entry_id`・`to_entry_id`・`amount`の組)ごとに、消込仕訳側の一時勘定の物理行を1行対応させ、その行のタグを対応する`to_entry`側のタグからコピーする**。1つの消込仕訳の一時勘定側を1行に集約せず、タグの組み合わせの数だけ行を分ける。[journal.md 1.3 貸借バランスの検証](./journal.md#13-貸借バランスの検証)は仕訳全体の借方合計・貸方合計の一致のみを見るため、行を細分化しても複式簿記としての整合性は崩れない。

```
例: スマホ分割(project=スマホ24回)とタブレット分割(project=タブレット12回)を
    同じ口座から毎月まとめて引き落とし、2件の分割払いを1件の消込でまとめて処理する

契約1(スマホ・暫定計上):     (借) 費用・通信費(端末)   120,000
                            (貸) 負債・未払金(分割)          120,000   project=スマホ24回

契約2(タブレット・暫定計上): (借) 費用・通信費(端末)    60,000
                            (貸) 負債・未払金(分割)           60,000   project=タブレット12回

1回目の口座引落CSV(1:N):    (借) 負債・未払金(分割)    10,000   project=スマホ24回
                            (借) 負債・未払金(分割)     5,000   project=タブレット12回
                            (貸) 資産・普通預金               15,000
  → journal_entry_links: (to_entry=契約1, amount=10,000), (to_entry=契約2, amount=5,000)
  → 消込残高(契約1) = 120,000 - 10,000 = 110,000
  → 消込残高(契約2) =  60,000 -  5,000 =  55,000

  …(2回目以降も同様の2行構成の消込を繰り返す。N:N)…
```

`journal_entry_links`側は`to_entry_id`ごとに独立した行として`amount`を持つため、1件の消込仕訳が何件・何種類のタグを一括で消し込んでいても、[1.6](#16-分割消込消込残高による完了判定)の消込残高は`to_entry`単位で個別に正しく計算できる。タグ別残高([projects.md 1.4](./projects.md#14-集計への影響))も、消込仕訳側の各行が正しいタグを持つ限り、同じ計算式でプロジェクトごとに正しく減っていく。

> **タグ(project_id・account_id)による候補検索は、消込/精算仕訳自身(from_entry側)を誤って含みうる(計画Issue #40)**
> 一時勘定の`project_id`・`account_id`は、消込/精算対象(`to_entry`側)だけでなく、本節の引き継ぎにより消込/精算仕訳自身(`from_entry`側)の一時勘定行にも同じ値が設定される。そのため、「このタグが付いた一時勘定行を持つ仕訳」を単純に検索して未消込候補の一覧を組み立てると、過去に作成済みの消込/精算仕訳自身が候補に紛れ込む。呼び出し側は、`settles`リンクの`from_entry_id`として自分自身が登場する仕訳(=それ自体が消込/精算仕訳であるもの)を候補から除外してから[1.6](#16-分割消込消込残高による完了判定)の消込残高計算・`findUnsettledEntries`等に渡す必要がある([expense-splitting.md 1.5](./expense-splitting.md#15-割勘の履歴と取り消し)の`findUnallocatedEntries`(`allocates`リンクの`from_entry`側を割勘仕訳とみなす判定)と対称的な考え方)。詳細は`docs/decisions.md`(2026-08-15)参照。

### 1.8 タグ不整合の予防と検知

[1.7](#17-タグ付き一時勘定の消込project_idhousehold_member_idの引き継ぎ)の自動コピーは「選定後にユーザーが手でタグを打ち直して間違える」ケースを防ぐが、それでも次の2つの経路でタグ不整合は起こりうる。

- 確定前のレビュー画面で、自動コピーされたタグをユーザーが誤って上書きしてしまう
- 確定後、[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の自由編集ルールにより、消込仕訳側の行のタグ(または元仕訳側のタグ)が後から書き換えられる

前者(作成時)と後者(事後編集)では、検証の強さを使い分ける。

**作成時のRepository層ハード検証**

`JournalEntryRepository`が`settles`リンクを作成する時点では、期待されるタグの組み合わせ(`to_entry`側の一時勘定行の`account_id`・`project_id`・`household_member_id`)は`to_entry`から一意に導出できている。したがってこの時点で、消込仕訳側に「同じ`account_id`・`project_id`・`household_member_id`を持ち、`amount`が`journal_entry_links.amount`以上の行」が実在するかを検証し、存在しなければ書き込みを拒否する。この検証は作成する1件の`journal_entry_links`行単位のものであり、`to_entry`に対する複数の`settles`リンクの累計が元の金額を超えるかどうか([1.6](#16-分割消込消込残高による完了判定)の「消込残高がマイナスになるケース(過剰消込)」参照)は対象外とする。

これは[journal.md 1.3 貸借バランスの検証](./journal.md#13-貸借バランスの検証)と同じ「Repository層がトランザクション書き込み直前に検証する」パターンであり、期待値が既に分かっている新規作成の場面に限定した検証である。[1.7](#17-タグ付き一時勘定の消込project_idhousehold_member_idの引き継ぎ)の自動コピーが機能していれば通常はこの検証で弾かれることはなく、確定前の手動上書きミスを最後に食い止める役割に留まる。

**事後のタグ不整合検知と警告**

確定後の仕訳編集は[journal.md 1.5](./journal.md#15-仕訳の編集削除)の通り常に自由であり、これを妨げるロックは設けない。[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)が「警告は取り込みを止めるものではない」としているのと同じ考え方で、事後のタグ不整合は検知しても編集をブロックしない。

検知の実装は新しい仕組みを追加せず、[journal.md 1.8 仕訳間の関係](./journal.md#18-仕訳間の関係journal_entry_links)で既に定義されている「仕訳の詳細画面から`from_entry_id = X OR to_entry_id = X`で関連する仕訳を辿れる」トラバーサルに乗せる。この画面表示のたびに、`to_entry`側の一時勘定行のタグと、リンクされた消込仕訳側の対応行のタグを比較し、食い違っていれば警告を出す。[reconciliation.md 1.5](./reconciliation.md#15-残高照合)の残高照合と同様、専用の状態カラムや不整合検知バッチは持たず、都度その場で比較するだけに留める。

> **原因の自動特定はしない**
> [reconciliation.md 1.5](./reconciliation.md#15-残高照合)の「警告メッセージからはどちらが原因かを特定できない」と同じく、タグ不整合の警告も「作成時の上書きミスか、事後編集による書き換えか」を自動判別しない。ユーザーが警告を見て、[journal.md 1.5](./journal.md#15-仕訳の編集削除)の通常の仕訳編集で訂正する、という既存の訂正フローに委ねる。専用の「タグ修正」機能は追加しない。
