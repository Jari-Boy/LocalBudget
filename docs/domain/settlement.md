# 消込(Settlement)ドメイン

[domain.md](../domain.md)(エントリポイント)から分割された、暫定計上(未払金・未収金)とCSV到着後の消込に関する詳細設計。

> **関連ドメイン**
> 本ドメインは、暫定計上された一時勘定を、CSV到着後に実際の外部取引と対応付けて解消する「消込」という会計処理そのものを定義する。消込の対応関係は、明示的なリンクテーブルではなく、一時勘定の明細行に付与する`settlement_batch_id`タグ(`settlement_batches`、計画Issue #133)の集計によって求める。1つの精算バッチ(割勘・分割払い等)に属する一時勘定行・精算行が同じ`settlement_batch_id`を共有し、残高はタグが一致する行の合算だけで決まる「補助元帳」方式である。サジェスト(外部明細取込時に未消込の一時勘定をサジェストする処理)は[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側で行う。一時勘定を経由する必要がある理由は[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)・[recurring-transactions.md 1.1](./recurring-transactions.md#11-位置づけ)側で扱う。
>
> **経緯**: 当初(〜計画Issue #132)は仕訳単位、その後明細行単位の`journal_entry_links`(`link_type = 'settles'`)というリンクテーブル方式だったが、計画Issue #133で実際の仕訳例を検討した結果、タグによるグルーピング・集計方式のほうがシンプルかつ堅牢と判断し置き換えた(経緯の詳細は`docs/decisions.md`参照)。`journal_entry_links`が本来担っていた「関連する仕訳の表示」という役割は、計画Issue #138で残高計算とは独立した軽量な仕組み(関連仕訳グループ、`journal_entry_link_groups`、[journal.md 1.8](./journal.md#18-関連仕訳グループjournal_entry_link_groups)参照)として実装され、`journal_entry_links`テーブル自体も完全に撤廃された。

## 1. 消込

### 1.1 位置づけ

消込とは、暫定計上された一時勘定(未払金・未収金)の残高を、実際の入出金(CSV由来の仕訳)と対応付けて解消する処理を指す。1回の暫定計上に対して消込が1回で完結するとは限らず、分割払いのように複数回に分けて段階的に解消していくケースもある([1.6 分割消込](#16-分割消込消込残高による完了判定)参照)。

家賃や給与のように、実際に現金が動くタイミングではなく発生した時点で記帳したい取引は、`liability`(未払金等)、または`asset`(未収金等、ただし`is_reconcilable = false`)の一時勘定を経由して暫定計上する。CSV到着後、その一時勘定を口座科目で消し込む。

一時勘定を経由する必要がある理由(口座科目への直接記帳が制限されていること)自体は本ドメインの関心事ではなく、[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)・[recurring-transactions.md 1.1](./recurring-transactions.md#11-位置づけ)側の制約に委ねる。本ドメインが定義するのは、一時勘定が既に存在する前提で、それをどう解消するか(消込仕訳の組み方・対応関係の記録方法)である。

この形は新しい概念ではなく、[journal.md 1.2 記帳の型](./journal.md#12-記帳の型)にある「カードで買い物→後日引き落とし」の未払金パターンと同じ構造である。

### 1.2 家賃・給与の例

```
例: 家賃(費用側)

暫定計上(手入力・定期取引): (借) 費用・家賃         80,000
                          (貸) 負債・未払金               80,000

CSV到着後の消込(CSV由来): (借) 負債・未払金         80,000
                          (貸) 資産・普通預金             80,000
```

```
例: 給与(収益側)

暫定計上(手入力・定期取引): (借) 資産・未収金        300,000
                          (貸) 収益・給与収入            300,000

CSV到着後の消込(CSV由来): (借) 資産・普通預金        250,000
                          (借) 費用・社会保険料         30,000
                          (借) 費用・所得税             20,000
                          (貸) 資産・未収金                  300,000
```

> **消込は金額が一致するとは限らない**
> 給与の例のように、天引き(社会保険料・所得税等)があると暫定計上額と実際の入金額はずれる。消込は単純な1:1の仕訳ではなく[journal.md 1.1](./journal.md#11-仕訳journalentryと仕訳明細journalline)の複合仕訳として行い、差額を按分する(天引き内訳を費用科目に分解するか、単に収益科目側の金額を実額に合わせるかはユーザーの任意)。
>
> 按分しきらず未払金・未収金に残高が残ることも許容する。これは異常ではなく、見込みと実績のズレとして正常に起こりうる状態である。ドメイン側は「消込は複合仕訳として組める」という枠組みのみ提供し、按分方法そのものは規定しない。

### 1.3 クレジットカード専用未払金との違い

[accounts.md 4章 資産・負債・収益・費用の統合登録フロー](./accounts.md#4-資産負債収益費用の統合登録フロー計画issue-102)で登録するクレジットカード未払金科目は`is_reconcilable = false`である。ここまでの家賃・給与の例で使った汎用未払金・未収金と同じく、記帳経路の制限は受けない。ただし役割は異なる。汎用未払金は「口座引落を待つ暫定計上」の受け皿として使うのに対し、カード専用未払金は主に**外部明細取込(利用明細CSV)由来の仕訳を直接記帳する対象**として使う。カードの支払い方法は口座振替とは限らないため`is_reconcilable = false`とした経緯は[accounts.md 4.5 なぜis_reconcilable = falseにするか](./accounts.md#45-なぜis_reconcilable--falseにするか)を参照。

```
例: クレジットカードの利用(カード専用未払金)

利用明細CSV由来:      (借) 費用・食費                3,000
                      (貸) 負債・未払金(楽天カード)          3,000
```

利用明細CSVをそのまま取り込んで記帳するため、家賃・給与のような暫定計上は経ない。この重複防止(突合)は`is_reconcilable`の値によらず働く独立した仕組みであるため([reconciliation.md 1.1](./reconciliation.md#11-位置づけ)参照)、`is_reconcilable = false`であってもカード単位で正しく機能する。

**支払い(消込)の2つの経路**

カードの支払い方法によって、消込の記帳経路が異なる。

- **口座振替(自動引き落とし)**: 口座側のCSVを取り込んだ際に生成される消込仕訳(`source_type = 'external_import'`)が、カード未払金を減少させる。

```
  口座CSV由来の消込:    (借) 負債・未払金(楽天カード)    50,000
                      (貸) 資産・普通預金             50,000
```

  `負債・未払金(楽天カード)`と`資産・普通預金`の両方を借方/貸方に使うが、どちらも同じ1つの仕訳の`source_type`で判定されるため、科目ごとに個別の外部参照を用意する必要はない([journal.md 1.7 作成経路(source_type)](./journal.md#17-作成経路source_type)参照)。

- **コンビニ払い等(現金・外部明細を伴わない経路)**: 対応する外部明細が存在しないため、`source_type = 'manual'`で消込仕訳を手入力する。カード未払金が`is_reconcilable = false`であるからこそ、この経路が可能になる([accounts.md 4.5](./accounts.md#45-なぜis_reconcilable--falseにするか)参照)。

いずれの経路でも、消込仕訳と消し込まれる元の利用明細仕訳との対応関係は、両方の一時勘定行に同じ`settlement_batch_id`を付与することで表現する(計画Issue #133)。複数の利用明細をまとめて消し込む複合仕訳でも、対象のすべての一時勘定行が同じ`settlement_batch_id`を共有していれば、集計(後述[1.6](#16-分割消込消込残高による完了判定))が自動的に正しい残高を求める。カードの利用明細に対応する`external_transaction_refs`はカード自身のCSVインポート時に作られたものがそのまま残り、消込側で新たに作る必要はない。

カードに対して残高照合が行われない理由は[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)の「対象科目」を参照。

### 1.4 一時勘定のis_reconcilable設定

`未収金`・`未払金`はCSVと直接照合されるべき本物の口座ではなく、あくまで内部の一時勘定である。そのため`is_reconcilable = false`として登録する([accounts.md](./accounts.md)参照)。`is_reconcilable = true`にしてしまうと、[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)のルールにより一時勘定自体への暫定計上(手入力)ができなくなり本末転倒になる。

### 1.5 他ドメインへの影響

- [accounts.md](./accounts.md)は、口座登録UXとは別に「一時勘定」として`is_reconcilable = false`の資産・負債科目をユーザーが作成できる必要がある([1.4](#14-一時勘定のis_reconcilable設定)参照)。
- 一時勘定行への`settlement_batch_id`タグの付与は、仕訳作成・精算操作を行うUI層(割勘起票フォーム・精算画面)の責務である。`JournalEntryRepository`は、タグが一時勘定(`is_reconcilable = false`の資産・負債科目、`isSettlementBatchTaggableAccount`)の行にのみ付いていることを書き込み前に検証し、それ以外の行に付いていれば`SettlementBatchOnNonTemporaryAccountError`で拒否する(create/update共通、計画Issue #144)。タグの値そのものの正しさ(どのバッチに付けるか)は検証せず、[1.8](#18-タグ不整合の予防と検知)の通りユーザーが残高表示で確認する。
- サジェスト(未消込の未払金・未収金の金額・日付の近似度等)の方法は、外部明細取込のレビュー画面側の実装課題として[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側に委ねる。本ドメインは「消込は複合仕訳として組める」という枠組みのみを規定する。「未消込」の判定基準そのものは[1.6 分割消込](#16-分割消込消込残高による完了判定)の消込残高に基づく。
- [settlement_batches](#2-精算バッチマスタsettlement_batches)(計画Issue #133): 割勘・分割払い等の精算バッチを識別する専用テーブル。`projects`とは独立しており、`project_id`(イベント)と`settlement_batch_id`(精算バッチ)は`journal_lines`上の別カラムとして同時に設定できる。精算残高が0になった時点の非アクティブ化提案は`settlement_batches`側の責務であり、本ドメインは消込残高([1.6](#16-分割消込消込残高による完了判定))を通じてその判定材料を提供するだけに留める(`projects.md`の非アクティブ化提案は計画Issue #133でイベント専用に縮小され、この責務を持たない)。

### 1.6 分割消込(消込残高による完了判定)

分割払い(例: スマホ本体代金を12回の口座引き落としで支払う)のように、1件の暫定計上を1回の消込では解消しきれず、複数回のCSV取込にまたがって段階的に解消していくケースがある。この節では、消込が「どこまで進んでいて、いつ完了したとみなせるか」を定義する。

**消込残高の定義**

ある一時勘定(`settlement_batch_id`・科目・世帯メンバー/取引先のタグの組)の消込残高は、そのタグに一致するすべての明細行を対象に、科目の区分(資産/負債)に応じた増加側を正としてamountを合算して求める(`calculateSettlementBatchBalance`)。

```
消込残高 = Σ(amount WHERE settlement_batch_id = 対象バッチ AND account_id = 対象科目
             AND household_member_id/counterparty_id = 対象タグ AND side = 増加側)
         - Σ(同条件 AND side = 減少側)
  (資産科目の増加側はdebit、負債科目の増加側はcredit)
```

消込残高が`0`になった時点で、その一時勘定は消込完了とみなす。明示的なリンクを使わないため、1件の一時勘定行に対して何件・何回の精算仕訳が積み重なっても、同じタグを共有している限り自動的に合算される。

> **なぜ専用のステータスカラムを持たないか**
> `journal_entries`や一時勘定科目に「消込済みフラグ」のような専用カラムを追加する案も検討したが、[recurring-transactions.md 2.1](./recurring-transactions.md#21-フィールド定義)の`max_occurrences`が生成済み件数を専用カウンタではなく`journal_entries`のCOUNTから都度算出するのと同じ理由で見送る。タグが一致する明細行のamountを集計すれば消込残高は一意に復元できるため、フラグと実際の明細行の状態がずれる(二重管理の)リスクを避けられる。
>
> サジェスト([statement-import.md 1.5](./statement-import.md#15-レコード処理フロー)手順5-a)が対象とする「未消込」も、この消込残高が`0`より大きい一時勘定を指す。

**例: スマホ本体代金の分割払い(12回)**

```
契約時の暫定計上(手入力):     (借) 費用・通信費(端末)   120,000
                            (貸) 負債・未払金(分割)          120,000

1回目のCSV到着後の消込:      (借) 負債・未払金(分割)    10,000
                            (貸) 資産・普通預金               10,000
  → 消込残高 = 120,000 - 10,000 = 110,000(未完了)

  …(2〜11回目も同様に毎月10,000円ずつ消込)…

12回目のCSV到着後の消込:     (借) 負債・未払金(分割)    10,000
                            (貸) 資産・普通預金               10,000
  → 消込残高 = 120,000 - 120,000 = 0(消込完了)
```

12回それぞれが独立した`journal_entries`(`source_type = 'external_import'`)であり、いずれも同じ`settlement_batch_id`(契約時の暫定計上仕訳の一時勘定行と同じタグ)を持つ一時勘定行を1行ずつ持つ。契約全体の残債務(いま消込残高がいくら残っているか)は、この消込残高の計算をUI表示のたびに行えばよく、[recurring-transactions.md 1.2](./recurring-transactions.md#12-自動生成-vs-レビュー確認)の見通し表示と同様、別テーブルに永続化する必要はない。

> **消込残高がマイナスになるケース(過剰消込)**
> ユーザーが誤って合計額を超えて消込仕訳を対応付けると消込残高は負になりうるが、DB制約としては禁止しない。[1.2 消込は金額が一致するとは限らない](#12-家賃給与の例)で許容している「按分しきらず残高が残る」ケースと同様、これも見込みと実績のズレとして起こりうる状態であり、訂正(消込仕訳の編集・削除)はユーザーの通常の仕訳編集操作([journal.md 1.5](./journal.md#15-仕訳の編集削除))に委ねる。ドメイン側で自動的な整合性回復は行わない。

> **タグ集計方式(計画Issue #133)により、対象の一時勘定科目が複数あっても誤って混入しない**
> 集計キーは`(settlement_batch_id, account_id, household_member_id または counterparty_id)`の組であり、`account_id`を常に含むため、[expense-splitting.md 1.3 世帯メンバー間の割勘](./expense-splitting.md#13-世帯メンバー間の割勘)のように**1件の仕訳が資産側・負債側それぞれ別の一時勘定行を持つ**場合でも、資産側の集計に負債側の金額が混入することはない(科目が異なれば別のグループとして集計される)。`calculateSettlementBatchBalance`はこのタグの組に一致する明細行だけを対象にするため、呼び出し側での事前絞り込みは不要である。
>
> この方式に至る前は、仕訳単位・のちに明細行単位の`journal_entry_links`(リンクテーブル)で同様の区別を実現していたが(計画Issue #110・#132)、実際の仕訳例を検討した結果、タグ集計方式のほうがシンプルかつ堅牢と判断し計画Issue #133で置き換えた。詳細な経緯は`docs/decisions.md`参照。

> **「毎月分を都度計上する」代替案との使い分け**
> 分割払いは、本節のように契約時に総額を一括計上して段階的に消し込む形のほか、[recurring-transactions.md 3章 大口費用の按分](./recurring-transactions.md#3-大口費用の按分)の枠組みで「毎月分を独立した一時勘定計上として都度生成し、その都度1:1で消し込む」形でも表現できる。前者は契約全体の残債務(消込残高)を一時勘定の集計として把握したい場合に、後者は各月の計上を完全に独立させて按分・解約時の扱いを[recurring-transactions.md 3.4](./recurring-transactions.md#34-按分ルールの終了)の既存の枠組みに乗せたい場合に向く。どちらもドメインとして矛盾なく成立するため、ユーザー(またはUI)がケースに応じて選べばよく、本ドメインはどちらか一方を強制しない。

### 1.7 タグ付き一時勘定の消込(settlement_batch_idによるタグ付け)

一時勘定(未払金・未収金、[expense-splitting.md 1.2 一時勘定(立替金/未払金)](./expense-splitting.md#12-一時勘定立替金未払金)の立替金も含む)を使い回す設計では、`journal_lines.settlement_batch_id`([settlement_batches](#2-精算バッチマスタsettlement_batches)、計画Issue #133)・`household_member_id`([household-members.md 1.2](./household-members.md#12-紐づけ対象と既定値の継承))で「どの分割払い契約/どの割勘バッチの残高か」をタグ付けする。これにより、[1.6](#16-分割消込消込残高による完了判定)の集計でタグ別残高を追うことができる。精算残高が0になった時点で、そのバッチの非アクティブ化が`settlement_batches`側からユーザーに提案される。

一時勘定行に`settlement_batch_id`タグを設定する経路は2つある。割勘起票フォームでは、新規の割勘仕訳を起票する時点で対象のバッチ・対象者をユーザーが明示的に選択し、その一時勘定行へ`settlement_batch_id`・`household_member_id`を直接設定する。精算画面では、既に起票済みの仕訳(CSV取込等で作成済みだが、まだどの精算バッチにも割り当てられていない一時勘定行を持つ仕訳)を選び、その行へ事後的に`settlement_batch_id`を割り当てる(計画Issue #139、[1.9](#19-精算画面の操作モデル計画issue-139)参照)。いずれの経路でも最終的には一時勘定行に`settlement_batch_id`・`household_member_id`を設定するだけであり、[1.6](#16-分割消込消込残高による完了判定)のタグ集計方式では「消込残高」と「タグ別残高」は同じ1つの計算(集計)に一本化されているため、旧来のリンク方式(計画Issue #132)で存在した「entry単位の消込残高とタグ単位の行集計が別経路で食い違う」という問題自体が構造上発生しない。

**選定の委譲**

一時勘定に紐づく未消込のタグ(バッチ・対象者・科目の組)がN件ある場合、そのうちどれを・いくらずつ今回の消込に対応させるかは、金額・日付の近似度だけから一意に決められる保証がない([statement-import.md 1.6 重複防止フロー](./statement-import.md#16-重複防止フロー)の「メモ: 候補選定ロジックの方向性」も参照)。この選定は、既存の[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)手順5-aで元々ユーザー(レビュー画面)に委ねられている判断であり、タグの有無によって新たに発生する負担ではない。「そもそも違う対象を選んでしまう」という選定自体の誤りは防げないが、これは消込機能に限らず、あらゆる手動選択操作に共通する限界であり、本ドメインが特別に解決する対象ではない。

**タグが異なる一時勘定をまとめて消し込む場合(1:N・N:N)**

[1.3 クレジットカード専用未払金との違い](#13-クレジットカード専用未払金との違い)のように1件の消込が複数の一時勘定を一括で消し込む場合(1:N)、[1.6](#16-分割消込消込残高による完了判定)の分割消込と組み合わされば1件の一時勘定が複数回・複数件まとめての消込を受けることもある(N:N)。いずれの場合も、対象ごとにタグ(どの分割払い契約か・どの割勘バッチか)が異なることがある。

原則は単純で、**消込仕訳の一時勘定側は、タグの組み合わせの数だけ行を分ける**。1つの消込仕訳の一時勘定側を1行に集約せず、対象のタグごとに別の行として明細に加える。[journal.md 1.3 貸借バランスの検証](./journal.md#13-貸借バランスの検証)は仕訳全体の借方合計・貸方合計の一致のみを見るため、行を細分化しても複式簿記としての整合性は崩れない。

```
例: スマホ分割(batch=スマホ24回)とタブレット分割(batch=タブレット12回)を
    同じ口座から毎月まとめて引き落とし、2件の分割払いを1件の消込でまとめて処理する

契約1(スマホ・暫定計上):     (借) 費用・通信費(端末)   120,000
                            (貸) 負債・未払金(分割)          120,000   settlement_batch_id=スマホ24回

契約2(タブレット・暫定計上): (借) 費用・通信費(端末)    60,000
                            (貸) 負債・未払金(分割)           60,000   settlement_batch_id=タブレット12回

1回目の口座引落CSV(1:N):    (借) 負債・未払金(分割)    10,000   settlement_batch_id=スマホ24回
                            (借) 負債・未払金(分割)     5,000   settlement_batch_id=タブレット12回
                            (貸) 資産・普通預金               15,000
  → 消込残高(スマホ24回)   = 120,000 - 10,000 = 110,000
  → 消込残高(タブレット12回) = 60,000 -  5,000 =  55,000

  …(2回目以降も同様の2行構成の消込を繰り返す。N:N)…
```

消込仕訳側の各行が正しいタグを持つ限り、[1.6](#16-分割消込消込残高による完了判定)の集計がバッチごとに個別に正しく減っていく。明示的なリンクを使わないため、1件の消込仕訳が何件・何種類のタグを一括で消し込んでいても、タグの組み合わせごとに行を分けるだけで足りる。

### 1.8 タグの編集について

[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の通り、確定後の仕訳編集(`settlement_batch_id`を含む)は常に自由であり、これを妨げるロックは設けない。明示的なリンクを使わないタグ集計方式(計画Issue #133)では、「作成時のタグ不整合検証」や「事後の不整合検知・警告」といった専用の仕組みは不要になった。タグを間違えて設定すると集計結果(未精算残高)がその場で誤って表示されるため、誤りの発見と訂正は[1.6](#16-分割消込消込残高による完了判定)の残高表示そのものがユーザーへのフィードバックとして機能する(例: 精算したのに残高が減らない、意図しないバッチの残高が変動する等)。これは[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)の「警告は取り込みを止めるものではない」という既存の考え方とも整合する。訂正は[journal.md 1.5](./journal.md#15-仕訳の編集削除)の通常の仕訳編集で行う。

### 1.9 精算画面の操作モデル(計画Issue #139)

精算画面(`SettlementScreen`)の操作モデルは「既存仕訳を選ぶ」が基本形である。当初は「精算額を入力→自動割り振り(FIFO)→相手科目を選択→精算するボタンで新規仕訳を作成する」という設計を検討したが、「科目の割り振りは明細を取り込んだとき(仕訳を作成したとき)に決まるものであり、精算バッチの画面で相手科目を選んで新規仕訳を作る、という設計はそもそも前提がおかしい」という指摘を受けて見直した経緯があり、詳細は`docs/decisions.md`を参照。

**画面の流れ**

1. 「対象者」(世帯メンバー or 取引先)と「科目」(立替金/未払金)を選ぶ。対象者ドロップダウンの候補(`listSettlementTargetOptions`)は、世帯メンバーは立替金/未払金の明細行の`household_member_id`から、取引先は`settlement_batches.counterparty_id`から収集する(明細行には取引先を直接紐付けられないため、[1.7](#17-タグ付き一時勘定の消込settlement_batch_idによるタグ付け)参照)。
2. 対象者・科目に一致する未精算バッチの一覧(バッチ名・対象の明細行サマリ・残高)を表示する(`findUnsettledSettlementBatchesForTarget`)。対象者が世帯メンバーの場合は`counterparty_id`が`null`のバッチに限り明細行の`household_member_id`を厳密に一致させ、取引先の場合は`settlement_batches.counterparty_id`が一致するバッチに限り`household_member_id`を問わずそのバッチ・科目の全行を合算する(誰が立て替えたかにかかわらず、取引先に対する残高は1つに集約する)。
3. バッチの「消込む仕訳を選ぶ」から、未割当(`settlement_batch_id`が`null`)の候補仕訳をチェックボックスで複数選択する(`findUnassignedAdvanceEntriesForTarget`)。候補の絞り込み条件は対象者の種類で異なる。
   - 世帯メンバーが対象者の場合: 明細行の`household_member_id`が対象者と厳密に一致する行。
   - 取引先が対象者の場合: `journal_lines.counterparty_id`は資産・負債の行に設定できない([counterparties.md 1.2](./counterparties.md#12-紐づけ対象))ため、未割当の行に「この取引先向け」という印を残す手段がない。そのため`household_member_id`が`null`(特定の世帯メンバーの支出として明細側で上書きされていない)行を候補とする設計を採用した。この場合、取引日・相手科目・金額を手掛かりに、ユーザーが候補一覧から正しい仕訳を選ぶ。
4. 選択した仕訳群の金額合計とバッチ残高を比較する。
   - **一致**: 「精算完了」ボタンのみ表示。選択した仕訳群の対象行に`settlement_batch_id`を割り当てるだけで、新規の仕訳は作らない(`buildJournalEntryUpdateWithAssignedSettlementBatch`、`JournalEntryRepository.update`)。
   - **不一致**: 「未精算として残す」(タグ付けのみ行い、差額をバッチ残高に残したまま次回以降の精算を待つ。[1.2](#12-家賃給与の例)・[1.6](#16-分割消込消込残高による完了判定)で許容している「按分しきらず残高が残る」ケースと同じ)と、「精算完了」(差額を損益として計上する調整仕訳を追加作成し、バッチ残高を0にする)の2択を提示する。
5. 候補仕訳が0件の場合に限り、ダイアログから新規に仕訳を手動作成できる(現金でのやり取り等、外部明細取込を経由しないケース)。

いずれの経路でタグ付け・作成した仕訳群も、既存のタグ付き仕訳と同じ関連仕訳グループへ参加させる(`JournalEntryLinkGroupRepository.joinOrCreateGroups`、[journal.md 1.8](./journal.md#18-関連仕訳グループjournal_entry_link_groups)、計画Issue #138)。

**差額の損益計上(調整仕訳)**

不一致時に「精算完了」を選ぶと、差額を「雑収入」(revenue)・「雑損失」(expense)のいずれかへ計上する調整仕訳を`buildSettlementJournalEntryInput`で追加作成する(一時勘定行は追加の`settlement_batch_id`タグを持つのみで、選択済みの仕訳群と合わせてバッチ残高がちょうど0になる)。どちらの科目を使うか、一時勘定行の借方/貸方をどちらにするかは、一時勘定の区分(資産/負債)によって反転する(`resolveSettlementAdjustment`)。

- 資産(立替金、相手が我々に返済する立場): 選択合計がバッチ残高より多い(多く受け取った)場合は雑収入。少ない(少なく受け取り、残りを放棄した)場合は雑損失。
- 負債(未払金、我々が返済する立場): 選択合計がバッチ残高より少ない(少なく払い、残りを免除された)場合は雑収入。多い(多く払った、過払い)場合は雑損失。

同じ「選択合計がバッチ残高より多い/少ない」という条件でも、資産/負債で損益の向きが反転する点に注意(資産側は相手からの受取額、負債側は自分からの支払額という向きの違いによる)。`resolveSettlementAdjustment`は、この判定と、`buildSettlementJournalEntryInput`の既存の借方/貸方ロジックをそのまま再利用するための実効区分(科目自体の区分を変更するものではない)を1つの純粋関数として提供する。

「雑収入」・「雑損失」は`is_system_managed`ではない通常のデフォルト科目として、Worker起動時に`seedSettlementAdjustmentAccounts`が科目名の有無で判定して冪等シードする(`seedDefaultAccounts`/`seedAdvanceAccounts`と同様のパターン)。ユーザーが生成された調整仕訳の科目を後から変更・削除したい場合は、通常の仕訳編集・科目管理操作で変更できる(削除された場合は次回のWorker起動時に本関数が再投入する)。

## 2. 精算バッチマスタ(settlement_batches)

割勘・分割払い等の精算バッチを識別する専用テーブル(計画Issue #133)。`projects`([projects.md](./projects.md))とは独立したエンティティであり、`journal_lines.settlement_batch_id`で一時勘定行にタグ付けする(`project_id`とは別カラムのため、1行が両方を同時に持てる)。

### 2.1 フィールド定義

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `id` | 精算バッチID | PK |
| `name` | バッチ名 | 例:「6月生活費」「スマホ24回払い」、自由記述 |
| `type` | 種別 | ENUM: `expense_splitting`(割勘)/`installment`(分割払い)。列挙値は実装時のユースケースに応じて追加しうる |
| `counterparty_id` | 取引先ID | [counterparties.md](./counterparties.md)参照、nullable。世帯外の相手との割勘バッチにのみ設定する(世帯メンバー間のバッチはnull、[expense-splitting.md 1.4](./expense-splitting.md#14-世帯外の相手との割勘)参照) |
| `created_at` | 作成日時 | |
| `updated_at` | 更新日時 | |

精算残高(紐づく資産・負債科目それぞれについて[1.6](#16-分割消込消込残高による完了判定)の計算を適用し、すべて0になった状態)が0になった時点で、非アクティブ化提案の対象になる(`projects.md`の非アクティブ化提案と同じ考え方、[projects.md 1.3 ライフサイクル](./projects.md#13-ライフサイクル)参照)。未記帳(紐づく資産・負債科目の仕訳明細が1件もない)場合は精算残高0とみなさない(同様の理由)。
