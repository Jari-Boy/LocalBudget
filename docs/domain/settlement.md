# 消込(Settlement)ドメイン

[domain.md](../domain.md)(エントリポイント)から分割された、暫定計上(未払金・未収金)とCSV到着後の消込に関する詳細設計。

> **関連ドメイン**
> 本ドメインは、暫定計上された一時勘定を、CSV到着後に実際の外部取引と対応付けて解消する「消込」という会計処理そのものを定義する。消込の対応関係は、明示的なリンクテーブルではなく、一時勘定の明細行に付与する`settlement_batch_id`タグ(`settlement_batches`、計画Issue #133)の集計によって求める。1つの精算バッチ(割勘)に属する一時勘定行・精算行が同じ`settlement_batch_id`を共有し、残高はタグが一致する行の合算だけで決まる「補助元帳」方式である。タグを付けられるのは割勘の一時勘定(システム管理の立替金・未払金)の行だけで、それ以外の一時勘定(カード未払金・汎用の未払金・未収金等)は科目の残高そのもので消込の進み具合を追う(計画Issue #167、[1.7](#17-タグ付き一時勘定の消込settlement_batch_idによるタグ付け)参照)。サジェスト(外部明細取込時に未消込の一時勘定をサジェストする処理)は[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側で行う。一時勘定を経由する必要がある理由は[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)・[recurring-transactions.md 1.1](./recurring-transactions.md#11-位置づけ)側で扱う。
>
> **経緯**: 当初(〜計画Issue #132)は仕訳単位、その後明細行単位の`journal_entry_links`(`link_type = 'settles'`)というリンクテーブル方式だったが、計画Issue #133で実際の仕訳例を検討した結果、タグによるグルーピング・集計方式のほうがシンプルかつ堅牢と判断し置き換えた(経緯の詳細は`docs/decisions.md`参照)。`journal_entry_links`が本来担っていた「関連する仕訳の表示」という役割は、計画Issue #138で残高計算とは独立した軽量な仕組み(関連仕訳グループ、`journal_entry_link_groups`、[journal.md 1.8](./journal.md#18-関連仕訳グループjournal_entry_link_groups)参照)として実装され、`journal_entry_links`テーブル自体も完全に撤廃された。

## 1. 消込

### 1.1 位置づけ

消込とは、暫定計上された一時勘定(未払金・未収金)の残高を、実際の入出金(CSV由来の仕訳)と対応付けて解消する処理を指す。1回の暫定計上に対して消込が1回で完結するとは限らず、分割払いのように複数回に分けて段階的に解消していくケースもある([1.6 分割消込](#16-分割消込消込残高による完了判定)参照)。

家賃や給与のように、実際に現金が動くタイミングではなく発生した時点で記帳したい取引は、`liability`(未払金等)、または`asset`(未収金等、ただし`is_reconcilable = false`)の一時勘定を経由して暫定計上する。CSV到着後、その一時勘定を口座科目で消し込む。

暫定計上に一時勘定を使う理由(CSV到着前に口座科目へ記帳すると二重計上になりうること。口座科目への直接記帳自体は[reconciliation.md 1.2](./reconciliation.md#12-is_reconcilable資産負債への直接記帳の制限)の通り許可されている)は本ドメインの関心事ではない。本ドメインが定義するのは、一時勘定が既に存在する前提で、それをどう解消するか(消込仕訳の組み方・対応関係の記録方法)である。

この形は新しい概念ではなく、[journal.md 1.2 記帳の型](./journal.md#12-記帳の型)にある「カードで買い物→後日引き落とし」の未払金パターンと同じ構造である。

### 1.2 家賃・給与の例

```
例: 家賃(費用側)

暫定計上(手入力・定期取引): (借) 費用・家賃         80,000
                          (貸) 負債・未払金               80,000

CSV到着後の消込(CSV由来): (借) 負債・未払金         80,000
                          (貸) 資産・普通預金             80,000
```

```
例: 給与(収益側)

暫定計上(手入力・定期取引): (借) 資産・未収金        300,000
                          (貸) 収益・給与収入            300,000

CSV到着後の消込(CSV由来): (借) 資産・普通預金        250,000
                          (借) 費用・社会保険料         30,000
                          (借) 費用・所得税             20,000
                          (貸) 資産・未収金                  300,000
```

> **消込は金額が一致するとは限らない**
> 給与の例のように、天引き(社会保険料・所得税等)があると暫定計上額と実際の入金額はずれる。消込は単純な1:1の仕訳ではなく[journal.md 1.1](./journal.md#11-仕訳journalentryと仕訳明細journalline)の複合仕訳として行い、差額を按分する(天引き内訳を費用科目に分解するか、単に収益科目側の金額を実額に合わせるかはユーザーの任意)。
>
> 按分しきらず未払金・未収金に残高が残ることも許容する。これは異常ではなく、見込みと実績のズレとして正常に起こりうる状態である。ドメイン側は「消込は複合仕訳として組める」という枠組みのみ提供し、按分方法そのものは規定しない。

### 1.3 クレジットカード専用未払金との違い

[accounts.md 4章 資産・負債・収益・費用の統合登録フロー](./accounts.md#4-資産負債収益費用の統合登録フロー計画issue-102)で登録するクレジットカード未払金科目は`is_reconcilable = false`である。ここまでの家賃・給与の例で使った汎用未払金・未収金と同じく、記帳経路の制限は受けない。ただし役割は異なる。汎用未払金は「口座引落を待つ暫定計上」の受け皿として使うのに対し、カード専用未払金は主に**外部明細取込(利用明細CSV)由来の仕訳を直接記帳する対象**として使う。カードの支払い方法は口座振替とは限らないため`is_reconcilable = false`とした経緯は[accounts.md 4.5 なぜis_reconcilable = falseにするか](./accounts.md#45-なぜis_reconcilable--falseにするか)を参照。

```
例: クレジットカードの利用(カード専用未払金)

利用明細CSV由来:      (借) 費用・食費                3,000
                      (貸) 負債・未払金(楽天カード)          3,000
```

利用明細CSVをそのまま取り込んで記帳するため、家賃・給与のような暫定計上は経ない。この重複防止(突合)は`is_reconcilable`の値によらず働く独立した仕組みであるため([reconciliation.md 1.1](./reconciliation.md#11-位置づけ)参照)、`is_reconcilable = false`であってもカード単位で正しく機能する。

**支払い(消込)の2つの経路**

カードの支払い方法によって、消込の記帳経路が異なる。

- **口座振替(自動引き落とし)**: 口座側のCSVを取り込んだ際に生成される消込仕訳(`source_type = 'external_import'`)が、カード未払金を減少させる。

```
  口座CSV由来の消込:    (借) 負債・未払金(楽天カード)    50,000
                      (貸) 資産・普通預金             50,000
```

  `負債・未払金(楽天カード)`と`資産・普通預金`の両方を借方/貸方に使うが、どちらも同じ1つの仕訳の`source_type`で判定されるため、科目ごとに個別の外部参照を用意する必要はない([journal.md 1.7 作成経路(source_type)](./journal.md#17-作成経路source_type)参照)。

- **コンビニ払い等(現金・外部明細を伴わない経路)**: 対応する外部明細が存在しないため、`source_type = 'manual'`で消込仕訳を手入力する。カード未払金が`is_reconcilable = false`であるからこそ、この経路が可能になる([accounts.md 4.5](./accounts.md#45-なぜis_reconcilable--falseにするか)参照)。

いずれの経路でも、カード未払金には精算バッチのタグを付けない(計画Issue #167)。カード未払金の科目残高がそのまま未払額であり、支払いのたびに残高が減っていくことで消込の進み具合がわかる。個々の利用明細と支払いの対応を見たい場合は、関連仕訳グループ([journal.md 1.8](./journal.md#18-関連仕訳グループjournal_entry_link_groups))で繋ぐ。カードの利用明細に対応する`external_transaction_refs`はカード自身のCSVインポート時に作られたものがそのまま残り、消込側で新たに作る必要はない。

カードに対して残高照合が行われない理由は[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)の「対象科目」を参照。

### 1.4 一時勘定のis_reconcilable設定

`未収金`・`未払金`はCSVと直接照合されるべき本物の口座ではなく、あくまで内部の一時勘定である。そのため`is_reconcilable = false`として登録する([accounts.md](./accounts.md)参照)。`is_reconcilable = true`にしてしまうと、一時勘定が本物の口座として残高照合([reconciliation.md 1.5](./reconciliation.md#15-残高照合))の対象になり、CSVと一致しない暫定計上が常に不一致警告を出してしまう。

### 1.5 他ドメインへの影響

- [accounts.md](./accounts.md)は、口座登録UXとは別に「一時勘定」として`is_reconcilable = false`の資産・負債科目をユーザーが作成できる必要がある([1.4](#14-一時勘定のis_reconcilable設定)参照)。
- 一時勘定行への`settlement_batch_id`タグの付与は、仕訳作成・精算操作を行うUI層(割勘起票フォーム・精算画面)の責務である。`JournalEntryRepository`は、タグが割勘の一時勘定(システム管理の立替金・未払金、`isSettlementBatchTaggableAccount`)の行にのみ付いていることを書き込み前に検証し、それ以外の行に付いていれば`SettlementBatchOnNonAdvanceAccountError`で拒否する(create/update共通、計画Issue #144、#167で対象を絞り込み)。タグの値そのものの正しさ(どのバッチに付けるか)は検証せず、[1.8](#18-タグ不整合の予防と検知)の通りユーザーが残高表示で確認する。
- サジェスト(未消込の未払金・未収金の金額・日付の近似度等)の方法は、外部明細取込のレビュー画面側の実装課題として[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)側に委ねる。本ドメインは「消込は複合仕訳として組める」という枠組みのみを規定する。「未消込」の判定基準そのものは[1.6 分割消込](#16-分割消込消込残高による完了判定)の消込残高に基づく。
- [settlement_batches](#2-精算バッチマスタsettlement_batches)(計画Issue #133): 割勘の精算バッチを識別する専用テーブル。`projects`とは独立しており、`project_id`(イベント)と`settlement_batch_id`(精算バッチ)は`journal_lines`上の別カラムとして同時に設定できる。精算残高が0になった時点の非アクティブ化提案は`settlement_batches`側の責務であり、本ドメインは消込残高([1.6](#16-分割消込消込残高による完了判定))を通じてその判定材料を提供するだけに留める(`projects.md`の非アクティブ化提案は計画Issue #133でイベント専用に縮小され、この責務を持たない)。

### 1.6 分割消込(消込残高による完了判定)

分割払い(例: スマホ本体代金を12回の口座引き落としで支払う)のように、1件の暫定計上を1回の消込では解消しきれず、複数回のCSV取込にまたがって段階的に解消していくケースがある。この節では、消込が「どこまで進んでいて、いつ完了したとみなせるか」を定義する。

**消込残高の定義**

ある一時勘定(`settlement_batch_id`・科目・世帯メンバー/取引先のタグの組)の消込残高は、そのタグに一致するすべての明細行を対象に、科目の区分(資産/負債)に応じた増加側を正としてamountを合算して求める(`calculateSettlementBatchBalance`)。

```
消込残高 = Σ(amount WHERE settlement_batch_id = 対象バッチ AND account_id = 対象科目
             AND household_member_id/counterparty_id = 対象タグ AND side = 増加側)
         - Σ(同条件 AND side = 減少側)
  (資産科目の増加側はdebit、負債科目の増加側はcredit)
```

消込残高が`0`になった時点で、その一時勘定は消込完了とみなす。明示的なリンクを使わないため、1件の一時勘定行に対して何件・何回の精算仕訳が積み重なっても、同じタグを共有している限り自動的に合算される。

> **タグ集計の対象は割勘の一時勘定だけ(計画Issue #167)**
> タグを付けられるのはシステム管理の立替金・未払金の行だけである([1.7](#17-タグ付き一時勘定の消込settlement_batch_idによるタグ付け))。それ以外の一時勘定(カード未払金・汎用の未払金・未収金等)にはタグがないため、消込残高は**その科目の残高**そのものになる。1つの科目の中で「どの契約の残りか」を分けて追いたい場合は、タグではなく科目を分ける(例:「未払金(スマホ分割)」)。

> **なぜ専用のステータスカラムを持たないか**
> `journal_entries`や一時勘定科目に「消込済みフラグ」のような専用カラムを追加する案も検討したが、[recurring-transactions.md 2.1](./recurring-transactions.md#21-フィールド定義)の`max_occurrences`が生成済み件数を専用カウンタではなく`journal_entries`のCOUNTから都度算出するのと同じ理由で見送る。タグが一致する明細行のamountを集計すれば消込残高は一意に復元できるため、フラグと実際の明細行の状態がずれる(二重管理の)リスクを避けられる。
>
> サジェスト([statement-import.md 1.5](./statement-import.md#15-レコード処理フロー)手順5-a)が対象とする「未消込」も、この消込残高が`0`より大きい一時勘定を指す。

**例: スマホ本体代金の分割払い(12回、契約ごとに科目を分ける)**

```
契約時の暫定計上(手入力):     (借) 費用・通信費(端末)          120,000
                            (貸) 負債・未払金(スマホ分割)            120,000

1回目のCSV到着後の消込:      (借) 負債・未払金(スマホ分割)     10,000
                            (貸) 資産・普通預金                      10,000
  → 未払金(スマホ分割)の残高 = 120,000 - 10,000 = 110,000(未完了)

  …(2〜11回目も同様に毎月10,000円ずつ消込)…

12回目のCSV到着後の消込:     (借) 負債・未払金(スマホ分割)     10,000
                            (貸) 資産・普通預金                      10,000
  → 未払金(スマホ分割)の残高 = 0(消込完了)
```

12回それぞれが独立した`journal_entries`(`source_type = 'external_import'`)であり、精算バッチのタグは付けない。契約全体の残債務は科目の残高として表示のたびに求めればよく、[recurring-transactions.md 1.2](./recurring-transactions.md#12-自動生成-vs-レビュー確認)の見通し表示と同様、別テーブルに永続化する必要はない。計画Issue #167以前は、汎用の「未払金(分割)」1科目に契約ごとの`settlement_batch_id`(`type = 'installment'`)を付けて区別する設計だったが、その残高を表示する画面がなく、科目を分ければ同じことができるため廃止した(`docs/decisions.md`参照)。

> **消込残高がマイナスになるケース(過剰消込)**
> ユーザーが誤って合計額を超えて消込仕訳を対応付けると消込残高は負になりうるが、DB制約としては禁止しない。[1.2 消込は金額が一致するとは限らない](#12-家賃給与の例)で許容している「按分しきらず残高が残る」ケースと同様、これも見込みと実績のズレとして起こりうる状態であり、訂正(消込仕訳の編集・削除)はユーザーの通常の仕訳編集操作([journal.md 1.5](./journal.md#15-仕訳の編集削除))に委ねる。ドメイン側で自動的な整合性回復は行わない。

> **タグ集計方式(計画Issue #133)により、対象の一時勘定科目が複数あっても誤って混入しない**
> 集計キーは`(settlement_batch_id, account_id, household_member_id または counterparty_id)`の組であり、`account_id`を常に含むため、[expense-splitting.md 1.3 世帯メンバー間の割勘](./expense-splitting.md#13-世帯メンバー間の割勘)のように**1件の仕訳が資産側・負債側それぞれ別の一時勘定行を持つ**場合でも、資産側の集計に負債側の金額が混入することはない(科目が異なれば別のグループとして集計される)。`calculateSettlementBatchBalance`はこのタグの組に一致する明細行だけを対象にするため、呼び出し側での事前絞り込みは不要である。
>
> この方式に至る前は、仕訳単位・のちに明細行単位の`journal_entry_links`(リンクテーブル)で同様の区別を実現していたが(計画Issue #110・#132)、実際の仕訳例を検討した結果、タグ集計方式のほうがシンプルかつ堅牢と判断し計画Issue #133で置き換えた。詳細な経緯は`docs/decisions.md`参照。

> **「毎月分を都度計上する」代替案との使い分け**
> 分割払いは、本節のように契約時に総額を一括計上して段階的に消し込む形のほか、[recurring-transactions.md 3章 大口費用の按分](./recurring-transactions.md#3-大口費用の按分)の枠組みで「毎月分を独立した一時勘定計上として都度生成し、その都度1:1で消し込む」形でも表現できる。前者は契約全体の残債務を契約専用の科目の残高として把握したい場合に、後者は各月の計上を完全に独立させて按分・解約時の扱いを[recurring-transactions.md 3.4](./recurring-transactions.md#34-按分ルールの終了)の既存の枠組みに乗せたい場合に向く。どちらもドメインとして矛盾なく成立するため、ユーザー(またはUI)がケースに応じて選べばよく、本ドメインはどちらか一方を強制しない。

### 1.7 タグ付き一時勘定の消込(settlement_batch_idによるタグ付け)

割勘の一時勘定([expense-splitting.md 1.2 一時勘定(立替金/未払金)](./expense-splitting.md#12-一時勘定立替金未払金)のシステム管理の立替金・未払金)を使い回す設計では、`journal_lines.settlement_batch_id`([settlement_batches](#2-精算バッチマスタsettlement_batches)、計画Issue #133)・`household_member_id`([household-members.md 1.2](./household-members.md#12-紐づけ対象と既定値の継承))で「どの割勘バッチ・誰の残高か」をタグ付けする。

タグを付けられるのはこの2科目の行だけである(計画Issue #167)。精算画面([1.9](#19-精算画面の操作モデル計画issue-139))が残高を見るのもこの2科目だけで、ほかの一時勘定や口座・損益科目に付けたタグはどの画面にも現れない。1つの科目の中に「誰の」「どの割勘の」分が混ざるのは割勘の一時勘定だけであり、それ以外は科目の残高そのもの、または科目を分けることで足りる([1.6](#16-分割消込消込残高による完了判定)参照)。判定は`isSettlementBatchTaggableAccount`(システム管理の資産・負債科目。システム管理の資産・負債はこの2科目しかない)にまとめ、仕訳画面・明細取込画面の選択欄の出し分けとRepositoryの書き込み時検証で共有する。これにより、[1.6](#16-分割消込消込残高による完了判定)の集計でタグ別残高を追うことができる。精算残高が0になった時点で、そのバッチの非アクティブ化が`settlement_batches`側からユーザーに提案される。

一時勘定行に`settlement_batch_id`タグを設定する経路は2つある。割勘起票フォームでは、新規の割勘仕訳を起票する時点で対象のバッチ・対象者をユーザーが明示的に選択し、その一時勘定行へ`settlement_batch_id`・`household_member_id`を直接設定する。精算画面では、既に起票済みの仕訳(CSV取込等で作成済みだが、まだどの精算バッチにも割り当てられていない一時勘定行を持つ仕訳)を選び、その行へ事後的に`settlement_batch_id`を割り当てる(計画Issue #139、[1.9](#19-精算画面の操作モデル計画issue-139)参照)。いずれの経路でも最終的には一時勘定行に`settlement_batch_id`・`household_member_id`を設定するだけであり、[1.6](#16-分割消込消込残高による完了判定)のタグ集計方式では「消込残高」と「タグ別残高」は同じ1つの計算(集計)に一本化されているため、旧来のリンク方式(計画Issue #132)で存在した「entry単位の消込残高とタグ単位の行集計が別経路で食い違う」という問題自体が構造上発生しない。

**選定の委譲**

一時勘定に紐づく未消込のタグ(バッチ・対象者・科目の組)がN件ある場合、そのうちどれを・いくらずつ今回の消込に対応させるかは、金額・日付の近似度だけから一意に決められる保証がない([statement-import.md 1.6 重複防止フロー](./statement-import.md#16-重複防止フロー)の「メモ: 候補選定ロジックの方向性」も参照)。この選定は、既存の[statement-import.md 1.5 レコード処理フロー](./statement-import.md#15-レコード処理フロー)手順5-aで元々ユーザー(レビュー画面)に委ねられている判断であり、タグの有無によって新たに発生する負担ではない。「そもそも違う対象を選んでしまう」という選定自体の誤りは防げないが、これは消込機能に限らず、あらゆる手動選択操作に共通する限界であり、本ドメインが特別に解決する対象ではない。

**タグが異なる一時勘定をまとめて消し込む場合(1:N・N:N)**

1件の入金・振込で複数の割勘バッチの立替金をまとめて精算する場合(1:N)、[1.6](#16-分割消込消込残高による完了判定)の分割消込と組み合わされば1つのバッチが複数回・複数件まとめての精算を受けることもある(N:N)。いずれの場合も、対象ごとにタグ(どの割勘バッチか・誰の分か)が異なることがある。

原則は単純で、**精算仕訳の一時勘定側は、タグの組み合わせの数だけ行を分ける**。1つの精算仕訳の一時勘定側を1行に集約せず、対象のタグごとに別の行として明細に加える。[journal.md 1.3 貸借バランスの検証](./journal.md#13-貸借バランスの検証)は仕訳全体の借方合計・貸方合計の一致のみを見るため、行を細分化しても複式簿記としての整合性は崩れない。

```
例: 配偶者Bに立て替えた「6月生活費」(batch=6月生活費)と「旅行」(batch=旅行)を、
    Bからの1回の振込でまとめて精算する

割勘1(6月生活費):           (借) 資産・立替金          30,000   household_member_id=B, settlement_batch_id=6月生活費
                            (貸) 費用・食費                   30,000

割勘2(旅行):                (借) 資産・立替金          20,000   household_member_id=B, settlement_batch_id=旅行
                            (貸) 費用・旅費                   20,000

Bからの振込CSV(1:N):        (借) 資産・普通預金        50,000
                            (貸) 資産・立替金                 30,000   household_member_id=B, settlement_batch_id=6月生活費
                            (貸) 資産・立替金                 20,000   household_member_id=B, settlement_batch_id=旅行
  → 未精算残高(6月生活費) = 30,000 - 30,000 = 0
  → 未精算残高(旅行)      = 20,000 - 20,000 = 0
```

精算仕訳側の各行が正しいタグを持つ限り、[1.6](#16-分割消込消込残高による完了判定)の集計がバッチごとに個別に正しく減っていく。明示的なリンクを使わないため、1件の精算仕訳が何件・何種類のタグを一括で消し込んでいても、タグの組み合わせごとに行を分けるだけで足りる。

### 1.8 タグの編集について

[journal.md 1.5 仕訳の編集・削除](./journal.md#15-仕訳の編集削除)の通り、確定後の仕訳編集(`settlement_batch_id`を含む)は常に自由であり、これを妨げるロックは設けない。明示的なリンクを使わないタグ集計方式(計画Issue #133)では、「作成時のタグ不整合検証」や「事後の不整合検知・警告」といった専用の仕組みは不要になった。タグを間違えて設定すると集計結果(未精算残高)がその場で誤って表示されるため、誤りの発見と訂正は[1.6](#16-分割消込消込残高による完了判定)の残高表示そのものがユーザーへのフィードバックとして機能する(例: 精算したのに残高が減らない、意図しないバッチの残高が変動する等)。これは[reconciliation.md 1.5 残高照合](./reconciliation.md#15-残高照合)の「警告は取り込みを止めるものではない」という既存の考え方とも整合する。訂正は[journal.md 1.5](./journal.md#15-仕訳の編集削除)の通常の仕訳編集で行う。

ただし「タグが立替金・未払金以外の行に付かない」という科目種別に関する検証は例外で、`JournalEntryRepository`のcreate/updateが書き込み前に行い、違反は`SettlementBatchOnNonAdvanceAccountError`で拒否する([1.5](#15-他ドメインへの影響)参照、計画Issue #144・#167)。ここで言う「不要になった検証」は、タグの値(どのバッチに付けるか)の整合性に関するものである。

仕訳画面(計画Issue #152)では、行ごとに精算バッチ欄が見えているため、タグ付きの行の科目を立替金・未払金以外へ変えると、欄が消えるのと同時にタグも外す。欄が見えていてタグの付け外しを画面で操作できるため、保存を拒否するより自然である。#144の「黙って消さずに更新を拒否する」は、タグが画面に表示されていなかった旧仕訳詳細画面での判断で、仕訳画面ではこの扱いに置き換えた(計画Issue #167、`docs/decisions.md`参照)。Repositoryの検証は、画面を経由しない書き込みへの防御として残る。

### 1.9 精算画面の操作モデル(計画Issue #139、計画Issue #153で割勘・精算画面の精算タブに刷新)

精算タブ(`SettleTab`、割勘・精算画面の2つ目のタブ)の操作モデルは「既存仕訳を選ぶ」が基本形である。当初は「精算額を入力→自動割り振り(FIFO)→相手科目を選択→精算するボタンで新規仕訳を作成する」という設計を検討したが、「科目の割り振りは明細を取り込んだとき(仕訳を作成したとき)に決まるものであり、精算バッチの画面で相手科目を選んで新規仕訳を作る、という設計はそもそも前提がおかしい」という指摘を受けて見直した経緯があり、詳細は`docs/decisions.md`を参照。計画Issue #153では、対象者と科目を先に選ぶ流れを、**精算バッチを先に選ぶ**流れに改めた(モデルは変えない)。

**画面の流れ**

1. 一覧で精算バッチを選ぶ。一覧には立替金と未払金の残高を別々の列で出す(`summarizeSettlementBatch`。同じバッチの立替金と未払金は合算も相殺もしない。明細が無い方は「-」)。「未精算」「精算済み」「すべて」で切り替える。**精算済みは、バッチの残高が0かどうかだけで判定する**(`isSettlementBatchBalanceZero`: バッチ内の(科目、世帯メンバー)の組ごとの残高がすべて0で、明細が1行以上ある。明細の無い方向は見ない)。仕訳を削除して残高が0でなくなれば、未精算に戻る。精算済みのバッチも選べて、紐づく仕訳を履歴として見られる。
2. 選んだバッチの「立替金を減らす」「未払金を減らす」の2枚のカードで残高と内訳を示し、方向を切り替える。対象者と比べる残高は`resolveSettlementTarget`が決める。残高は「科目×世帯メンバー」で持ち、バッチはイベントをまとめるだけなので、バッチが世帯内でも世帯外の相手でも、その方向で残高が残っている世帯メンバーを対象者にして、そのメンバーの残高と比べる(すべての行に世帯メンバーが入る前提。制約の実装は別Issue)。
3. 「精算する仕訳を探す」で、未割当(`settlement_batch_id`が`null`)の候補仕訳をチェックボックスで複数選択する(`findUnassignedAdvanceEntriesForTarget`)。候補は「科目、方向(貸借)、対象者」を**同じ行で**満たす固定条件で、それ以外の絞り込み(ポップアップの絞り込み)は仕訳全体で判定する。方向は、立替金を減らす精算なら立替金の貸方、未払金を減らす精算なら未払金の借方の行である。対象者の条件は次のとおり。
   - 世帯メンバーが対象者の場合: 明細行の`household_member_id`が対象者と厳密に一致する行。
   - 世帯外の相手のバッチも対象者は世帯メンバーである。`journal_lines.counterparty_id`は資産・負債の行に設定できない([counterparties.md 1.2](./counterparties.md#12-紐づけ対象))ため、誰の残高かは行の世帯メンバーで表し、相手はバッチの取引先で表す。精算の行にも同じ世帯メンバーを付ける。
4. 選択した仕訳群の金額合計と、選んだ方向の残高を比較する(別の方向の残高とは比べない)。
   - **一致**: 「精算完了」ボタンのみ表示。選択した仕訳群の対象行に`settlement_batch_id`を割り当てるだけで、新規の仕訳は作らない(`buildJournalEntryUpdateWithAssignedSettlementBatch`、`JournalEntryRepository.update`)。
   - **不一致**: 「未精算として残す」(タグ付けのみ行い、差額をバッチ残高に残したまま次回以降の精算を待つ。[1.2](#12-家賃給与の例)・[1.6](#16-分割消込消込残高による完了判定)で許容している「按分しきらず残高が残る」ケースと同じ)と、「精算完了」(差額を損益として計上する調整仕訳を追加作成し、バッチ残高を0にする)の2択を提示する。
5. 候補の有無によらず、「+ 精算の仕訳を起票」から精算の仕訳を新規に起票できる(現金でのやり取りなど、外部明細取込を経由しないケース。計画Issue #153で、従来の「候補が0件のときだけ」を「常に」に変えた)。起票した仕訳は選んだ方向の科目にバッチのタグを付ける。
6. バッチ名と世帯外の相手(取引先)を、精算タブから編集できる(`SettlementBatchRepository.update`)。
7. 未精算のバッチは、「このバッチを削除」(2回押して確定)で、アプリが作った割勘仕訳ごと削除できる(`planSettlementBatchDeletion`)。削除できるのは、バッチのタグが付いた仕訳がすべて割勘仕訳(`expense_splitting`)のバッチだけで、削除するのはその割勘仕訳とバッチである。元の支出の仕訳は触らない。精算で紐づけた既存の仕訳や精算の仕訳が1件でもあれば、実際の取引の記録を消さないために削除できない。明細の無い空のバッチは削除できる。
8. 「このバッチの仕訳」の、残高を減らす側の行(立替金の貸方・未払金の借方)は、「紐づけを解除」(2回押して確定)で`settlement_batch_id`を外せる(精算済みのバッチでも可)。仕訳は削除せず、行は候補に戻り、バッチの残高が増える。関連仕訳グループの所属は変えない。

いずれの経路でタグ付け・作成した仕訳群も、既存のタグ付き仕訳と同じ関連仕訳グループへ参加させる(`JournalEntryLinkGroupRepository.joinOrCreateGroups`、[journal.md 1.8](./journal.md#18-関連仕訳グループjournal_entry_link_groups)、計画Issue #138)。書き込みは`submitSettlement`(`tagCandidatesToBatch`・`createSettlementEntry`)にまとめてある。

**差額の損益計上(調整仕訳)**

不一致時に「精算完了」を選ぶと、差額を「雑収入」(revenue)・「雑損失」(expense)のいずれかへ計上する調整仕訳を`buildSettlementJournalEntryInput`で追加作成する(一時勘定行は追加の`settlement_batch_id`タグを持つのみで、選択済みの仕訳群と合わせてバッチ残高がちょうど0になる)。どちらの科目を使うか、一時勘定行の借方/貸方をどちらにするかは、一時勘定の区分(資産/負債)によって反転する(`resolveSettlementAdjustment`)。

- 資産(立替金、相手が我々に返済する立場): 選択合計がバッチ残高より多い(多く受け取った)場合は雑収入。少ない(少なく受け取り、残りを放棄した)場合は雑損失。
- 負債(未払金、我々が返済する立場): 選択合計がバッチ残高より少ない(少なく払い、残りを免除された)場合は雑収入。多い(多く払った、過払い)場合は雑損失。

同じ「選択合計がバッチ残高より多い/少ない」という条件でも、資産/負債で損益の向きが反転する点に注意(資産側は相手からの受取額、負債側は自分からの支払額という向きの違いによる)。`resolveSettlementAdjustment`は、この判定と、`buildSettlementJournalEntryInput`の既存の借方/貸方ロジックをそのまま再利用するための実効区分(科目自体の区分を変更するものではない)を1つの純粋関数として提供する。

「雑収入」・「雑損失」は`is_system_managed`ではない通常のデフォルト科目として、Worker起動時に`seedSettlementAdjustmentAccounts`が科目名の有無で判定して冪等シードする(`seedDefaultAccounts`/`seedAdvanceAccounts`と同様のパターン)。ユーザーが生成された調整仕訳の科目を後から変更・削除したい場合は、通常の仕訳編集・科目管理操作で変更できる(削除された場合は次回のWorker起動時に本関数が再投入する)。

## 2. 精算バッチマスタ(settlement_batches)

割勘の精算バッチを識別する専用テーブル(計画Issue #133)。`projects`([projects.md](./projects.md))とは独立したエンティティであり、`journal_lines.settlement_batch_id`で立替金・未払金の行にタグ付けする(`project_id`とは別カラムのため、1行が両方を同時に持てる)。

### 2.1 フィールド定義

| `name` | バッチ名 | 例:「6月生活費」「スマホ24回払い」、自由記述 |
| `type` | 種別 | ENUM: `expense_splitting`(割勘)のみ。分割払い(`installment`)は計画Issue #167で廃止した([1.6](#16-分割消込消込残高による完了判定)参照) |
| `counterparty_id` | 取引先ID | [counterparties.md](./counterparties.md)参照、nullable。世帯外の相手との割勘バッチにのみ設定する(世帯メンバー間のバッチはnull、[expense-splitting.md 1.4](./expense-splitting.md#14-世帯外の相手との割勘)参照) |
| `created_at` | 作成日時 | |
| `updated_at` | 更新日時 | |

精算残高(紐づく資産・負債科目それぞれについて[1.6](#16-分割消込消込残高による完了判定)の計算を適用し、すべて0になった状態)が0になった時点で、非アクティブ化提案の対象になる(`projects.md`の非アクティブ化提案と同じ考え方、[projects.md 1.3 ライフサイクル](./projects.md#13-ライフサイクル)参照)。未記帳(紐づく資産・負債科目の仕訳明細が1件もない)場合は精算残高0とみなさない(同様の理由)。

### 2.2 DDL
