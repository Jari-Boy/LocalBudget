## 1. 世帯メンバー

### 1.1 位置づけ

世帯メンバーは「誰の口座/誰の取引か」を表す軸であり、プロジェクト(目的)・勘定科目(用途)とも独立する。1つの家計簿を世帯で共有し、個人ごとの資産・支出を把握したい、というニーズに応える。

**認証・ログインの概念ではない。** このアプリはLocal-first・サーバーレスであり([architecture.md](../architecture.md) 1章・11章)、アクセス制御や権限管理は持たない。全データは同一のローカルDB内にあり、世帯メンバーはあくまで集計・表示のための分類ラベルである。

> **命名について**
> テーブル名は`users`ではなく`household_members`(世帯メンバー)とする。`users`は「アプリにログインする主体」を連想させる。将来アプリの利用者アカウント機能(認証)を追加する際に概念が衝突しうるため、意図的に区別する。

### 1.2 紐づけ対象と明細行の世帯メンバーの決め方

プロジェクトとは異なり、世帯メンバーは **全区分(資産・負債・純資産・収益・費用)に適用可能** とする。ただし、口座(BS科目)の名義は取引のたびに変わるものではなく、口座に固定される性質がある。

**すべての仕訳明細行(`journal_lines.household_member_id`)は、常に実際の世帯メンバーを持つ(NOT NULL、計画Issue #169)。** 以前は「明細側がNULLなら科目の既定値、無ければ起票者を継承する」3段階の継承(`resolveEffectiveHouseholdMemberId`)で読み取り時に解決していたが、これを廃止した。明細行を見るだけで誰の行かが確定し、読み取り側(世帯メンバー別集計・財務諸表のフィルタ・仕訳のフィルタ等)に継承規則を分散させない。読み取り側は科目の既定値や起票者へフォールバックせず、明細行の値をそのまま使う。強制の場所はDBのNOT NULL制約である(判断の経緯は`docs/decisions.md` 2026-11-09、計画Issue #169)。

#### 書き込み時の決め方

明細行を保存するとき、世帯メンバーは次の優先順で決める(`resolveLineHouseholdMemberId`、`src/domain/journal/resolveLineHouseholdMemberId.ts`)。

| 優先 | 値 | 役割 |
|---|---|---|
| 1 | 科目の既定メンバー(`accounts.household_member_id`) | 口座・科目自体の既定の名義。例:「三菱UFJ銀行」口座は夫名義。設定されている場合は**明示的に保存され、上書きできない** |
| 2 | 指定されたメンバー | 画面で選んだ、または入力に含まれる値。科目に既定メンバーが無い場合のみ有効 |
| 3 | 起票者(`journal_entries.household_member_id`、NOT NULL) | 上記のどちらも無いときの既定値([journal.md 1.1](./journal.md#11-仕訳journalentryと仕訳明細journalline)参照) |

科目に既定メンバーがある行は、既定値を明示的に保存する(NULLにして継承させない)。**既定メンバーのある科目の行に異なる値を入れることは、DDLトリガー(`docs/schema/journal.sql`)で禁止される**([journal.md 2.2](./journal.md#22-ddl)参照)。口座の名義は口座自体に固定される性質を持ち、これを許容すると口座単位のメンバー別集計(`aggregateByHouseholdMember`)と口座自体の残高が食い違いうるためである。INSERTは科目の既定値と異なる値を拒否する。UPDATEは`household_member_id`を変えない限り許可し(科目の既定メンバーを後から変えて旧メンバーのまま残した行の金額等を編集できるようにするため)、変える場合だけ科目の既定値との一致を検証する。

`accounts.household_member_id`自体は引き続き`NULL`を許容し、口座自体の既定名義が無い(誰か個人に固定しない)ことを表す。生活費口座のように誰か個人に紐づける必要のない口座は`NULL`のままでよい。この場合も、その科目を使う明細行は指定されたメンバー、無ければ起票者の世帯メンバーを持つ(「誰にも紐づかない」行は存在しない)。

```
例1: 夫名義の普通預金口座(account.household_member_id = 夫)から、
     妻が買い物をした

(借) 費用・食費        4,000   line.household_member_id = 妻 (科目に既定値が無いため指定できる)
(貸) 資産・普通預金            4,000   line.household_member_id = 夫 (科目の既定値が保存される)

例2: 世帯共通の現金口座(account.household_member_id = NULL)から、
     夫が起票者として買い物を記録した。明細側は指定なし

(借) 費用・食費        1,500   line.household_member_id = 夫 (起票者)
(貸) 資産・現金               1,500   line.household_member_id = 夫 (起票者)
```

#### 起票者の変更と明細行の追従

仕訳画面の詳細パネルで起票者を選択・変更できる(`JournalEntryRepository.update`は任意の`householdMemberId`で起票者の変更を保存する)。起票者を変えると、**旧起票者のままで、科目に既定メンバーがない明細行だけ**が新しい起票者に追従する(`followBookkeeper`)。科目の既定メンバーで固定された行と、手で別のメンバーにした行は動かない。明細行の世帯メンバー欄に「メンバーなし」は無く、常に1人を選ぶ。科目を変えた行は、科目に既定メンバーがあればその値に切り替わる(`memberAfterAccountChange`)。未選択の行があると保存できない(理由`unselectedMember`)。

#### 下書き

下書きの明細行(`journal_entry_draft_lines.household_member_id`)はNULL許容のままで、下書き段階の未入力を許す。確定時に世帯メンバーのない明細行があれば`JournalLineHouseholdMemberRequiredError`で確定を拒否する。下書きを再開したときと、新規仕訳・定期取引の提案を開いたときは、未入力の世帯メンバーを科目の既定メンバー、無ければ起票者で補う。

#### 科目の既定メンバーを変えるとき

科目の既定メンバーを別のメンバーへ変えるとき、新しい既定メンバーと異なる世帯メンバーの明細行があれば、その件数を示す確認ダイアログ(`DefaultMemberChangeDialog`)を出し、「過去の明細行も更新する」「そのまま残す」を選ばせる(`AccountRepository.update`の`options.updateExistingLines`。科目の更新と明細行の更新は同一トランザクション)。既定メンバーの解除(NULLへの変更)では明細行を変えない。

どちらかに固定しないのは、既定メンバーの変更に2種類あるためである。設定ミスの修正なら過去も更新するのが正しく、名義が実際に変わった場合や既定メンバーの新規設定なら過去は履歴としてそのまま残すのが正しい。「更新する」を選ぶと行ごとに別メンバーを指定していた行も上書きされ、精算済みバッチの残高が崩れて未精算に戻りうる点に注意する。

#### 移行

開発用DBは作り直す前提で、既存データのマイグレーション(NULL行の補完・テーブル再作成)は行わない。NULL行を含む、または`journal_lines.household_member_id`がNULL許容の旧スキーマのバックアップの取込は対象外で、取込時のスキーマ検証(`assertValidDatabaseSchema`)が`InvalidBackupFileError`で拒否する。

### 1.3 ライフサイクル

プロジェクト・勘定科目と同様、削除ではなく非アクティブ化を基本とする。

| 操作 | 条件 | 扱い |
|---|---|---|
| 物理削除 | 科目の名義・仕訳明細・仕訳の起票者・定期取引ルールのいずれでも使われていない | 可 |
| 物理削除 | 上記のいずれかで使用中 | 不可(非アクティブ化のみ)。`prevent_delete_member_with_references`トリガーと外部キー制約がDBレベルで拒否する(`masterDeletionConstraints.test.ts`で確認済み、計画Issue #154)。画面は事前に判定し、使用中の理由を表示する |
| 名称変更 | 常に | 可 |
| 非アクティブ化 | 任意(例: 世帯構成の変化) | 過去集計はそのまま表示、新規の紐づけでは選択不可 |

### 1.4 集計への影響

メンバー別の集計は、[financial-statements.md 2章 財務諸表(FS)](./financial-statements.md#2-財務諸表fs)の期間集計、[projects.md 1.4 集計への影響](./projects.md#14-集計への影響)のプロジェクト別集計、[counterparties.md 1.7 集計への影響](./counterparties.md#17-集計への影響)の取引先別集計と独立した軸として提供する。仕組みはプロジェクト別・取引先別と同じで、フィルター条件(どの軸で絞り込むか)が違うだけである。

```
メンバー別合計(household_member、区分に応じて符号反転) =
  Σ(amount WHERE side = 増加側) - Σ(amount WHERE side = 減少側)
  (明細行のhousehold_member_id = 対象household_member、期間で絞らず全期間が既定)
```

期間・プロジェクト・世帯メンバーの3軸は互いに独立しており、任意の組み合わせで絞り込める(例:「今月・アメリカ旅行・夫」の支出)。

### 1.5 グループ(複数メンバーの集合)

「夫婦共有口座」のように、特定の複数メンバーの集合に紐づく口座・支出を表現するため、`household_members`は「個人」と「グループ」を同じテーブル・同じ形式で扱う。`is_group`フラグで区別し、グループの場合は所属する個人メンバーを中間テーブル(`household_member_group_memberships`)で管理する。

```
例: 「夫婦」というグループを作り、「夫」「妻」を所属させる

household_members:
  (1, "夫",   is_group=false)
  (2, "妻",   is_group=false)
  (3, "夫婦", is_group=true)

household_member_group_memberships:
  (group_id=3, member_id=1)
  (group_id=3, member_id=2)
```

`accounts.household_member_id`・`journal_lines.household_member_id`は、個人・グループのどちらのIDも区別なく指定できる。既存の明細行の世帯メンバーの決め方([1.2](#12-紐づけ対象と明細行の世帯メンバーの決め方))や集計ロジック([1.4](#14-集計への影響))はグループに対してもそのまま適用される。グループは「所属者を持つ、もう1つの`household_member`」に過ぎない。

**グループは独立した集計単位として扱う。** 「夫婦」グループの残高は「夫」「妻」個人の集計には含まれない。二重計上を避け、個人の資産・支出を正確に把握できるようにするための判断である。

世帯全体を俯瞰したい場合は、UI側で個人とグループを横断的に合算する。

```
世帯合計 = Σ(household_member = 夫) + Σ(household_member = 妻) + Σ(household_member = 夫婦) + ...
```

[1.2](#12-紐づけ対象と明細行の世帯メンバーの決め方)の「`accounts.household_member_id = NULL`」との違いに注意する。`NULL`は「その口座自体には特定の個人を固定しない」ことを表す**口座の既定値の状態**であるのに対し、グループは「夫婦」のように具体的な構成メンバーが明示された共有である。両者は併存してよい。例えば子供の教育費用の口座のように具体的な名義を持たせたくない場合は引き続き`accounts.household_member_id = NULL`を使い、「誰と誰の共有か」を集計上区別したい場合にグループを使う。なお[1.2](#12-紐づけ対象と明細行の世帯メンバーの決め方)の通り、口座の既定値が`NULL`でも各明細行は常に実際の世帯メンバーを持ち「誰にも紐づかない」行は存在しないため、「誰にも紐づかない扱いにしたい」という意図であればグループではなく個々の取引の起票者・明細側の指定をそのまま使えばよい。

グループのネストは許可しない(グループの中に別のグループを含めることはできない)。個人が複数のグループに同時に所属することは許可する(多対多)。

> **`is_group`は変更不可**
> `category`([accounts.md 3.2 DDL](./accounts.md#32-ddl))と同様、`is_group`はレコード作成後の変更を禁止する。個人として作成したメンバーを後からグループへ、あるいはその逆へ変更すると、既存の`accounts.household_member_id`等の参照が指し示す意味が変わってしまうためである。

## 2. 世帯メンバーマスタ(household_members)

### 2.1 フィールド定義

**household_members**

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `id` | メンバーID | PK |
| `name` | 表示名 | 例:「夫」「妻」「夫婦」、自由記述 |
| `is_group` | 個人かグループか | `false`=個人、`true`=グループ。作成後の変更不可([1.5](#15-グループ複数メンバーの集合)参照) |
| `is_active` | 有効/非アクティブ | falseにしても過去仕訳・過去集計に影響なし |
| `created_at` | 作成日時 | |
| `updated_at` | 更新日時 | |

認証情報(パスワード・メールアドレス等)は一切持たない。勘定科目・プロジェクトと同様、識別のためのラベルに過ぎない([1.1](#11-位置づけ)参照)。

**household_member_group_memberships**

| カラム | 内容 | 制約・備考 |
|---|---|---|
| `group_id` | グループ側のID | FK、`is_group=true`のレコードのみ許可(TRIGGERで強制) |
| `member_id` | 所属する個人のID | FK、`is_group=false`のレコードのみ許可、ネスト禁止(TRIGGERで強制) |

複合主キー(`group_id`, `member_id`)で組み合わせの重複登録を防ぐ。

### 2.2 DDL

実装: [schema/household_members.sql](../schema/household_members.sql)
